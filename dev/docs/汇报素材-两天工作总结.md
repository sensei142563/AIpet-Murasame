## 三、Jev：给桌宠加"本地决策层"（本次的新架构工作）

### 1. 先弄清 Jev 是什么（一手资料）

> **Jev 不生成文本。** 给它一段 **state** + 若干**带类型的问题**，它在 **70–500ms** 内答完：从给定选项里选一个、在量表上打分、给 0–1 概率，**每个答案带置信度**。（TypeSafe 的 "System One" 模型；2026-09-15 开放 early access）

**官方 API 规格**（从 `docs.typesafe.ai/api` 抓到的真规格）：
```
POST https://api.typesafe.ai/v1/systemone      Authorization: Bearer <API_KEY>
{ "model": "jev-latest",
  "state": <string|object|array>,
  "questions": { "<key>": { "type": "choice"|"score",
                            "instructions": "...",
                            "criteria": { "<选项>": "<描述>" } } } }      # ≤255 选项
→ 答案按同一 key 返回；choice/score 带 confidence(0~1)
```

### 2. 关键现实约束与我们的选择

- **区域限制**：TypeSafe 控制台对本地区返回 **HTTP 451（Unavailable For Legal Reasons）**；付费走银联也走不通 → **决定不领 key**。
- **因此走"本地 + 本机中转"**：
  - 手机 **不直连** TypeSafe；手机把判断题发给**电脑端**，电脑去调 Jev，再把答案回给手机 → **手机侧零区域问题**，且**判断都在本地完成**。
  - 同时把这条线做成**实现可替换**：云端 Jev 与将来的**本地开源复现**共用同一请求/响应形状 → 换实现时**调用点一行都不用改**。

### 3. 已交付的四层（全部有测试）

| 层 | 文件 | 设计要点 | 测试 |
|---|---|---|---|
| 电脑端客户端 | `tool/jev.py` | 零新依赖（标准库 urllib）；**绝不抛异常**；答案**必须在候选集内**；**无 key 不发任何请求**；`TYPESAFE_BASE_URL` 可指向代理/自建网关 | `tests/test_jev.py`（含"**校验请求形状**"用例） |
| 电脑端接口 | `api.py` → `POST /jev/choose` | 逻辑抽成纯同步函数便于离线测试；无 key/异常 → `{name: null}`，**手机端永远拿到可解析 JSON** | `tests/test_jev_endpoint.py` |
| 真实业务接入 | `qq/qq_chat.py` | 「发哪个表情包」由 Jev 从角色 `biaoqingbao/` 的**文件名候选**里选；**置信度 < 0.5 不发** | 与上两项共 **14 passed** |
| 手机端客户端 | `chatter: bot/chat/JevClient.kt` | 默认禁用（地址空 → 一个请求都不发）；连接 1.5s / 读 4s 超时；严格校验候选 | 编译通过 |

> 为什么选"表情包"做第一个落点：现在的做法是**让大模型在回复里写 `[表情:名称]`**（拼 prompt + 生成文本 + 正则解析）——本质上就是一道"从 N 个文件名里选 1 个"的**封闭选择题**，正是 Jev 的设计用途；而大模型挑错/漏标是常见失败。

| # | 假设 | 结论 | 证据 |
|---|---|---|---|
| 1 | 接线/调用方式错 | ❌ 排除 | 埋点逐步有日志（`speak()` → `init()` → `模型类型=VITS` → `准备构造…`） |

| 3 | 配置参数错 | ❌ 排除 | **用全空配置构造，同样挂死** |
| 4 | 原生库冲突（Cubism × ONNX 同进程） | ❌ 排除 | **在 App 启动、完全未加载 Live2D 时构造，同样挂死** |
| 5 | 换个构造重载（可传 Executor） | ❌ 不存在 | `javap` 证明该 AAR 只有那一个公开构造（我原以为的重载是 Kotlin 合成签名） |
| 6 | 线程/Looper 上下文 | ⬜ 待验 | 已备好"主线程直接构造"的探针（未跑完） |

**结论（精确表述）**：不是"手机不能合成"，而是**我们集成的这个库（sherpa-onnx v1.13.5）在这个 App 里"构造引擎"就挂死**，且**与配置、与原生库冲突都无关**。
**出路**：① 换封装（ONNX Runtime 直跑，参考 NekoSpeak：Kotlin + ONNX Runtime，100% 离线，含零样本克隆）② **电脑生成 + 手机播放**（最稳）。

## 六、工程方法论（汇报的加分项）

1. **判据要选不会撒谎的那个**：
   - 判断"是否发生了页面切换"用 **pid 是否变化**（进程不变=没重启）；判断窗口可信用 **`mHasSurface=true` 且 `isReadyForDisplay()=true`** 双断言。
   - 华为机型过滤 logcat → **让 App 自己写日志文件**。
   - 点击是否生效 → **在回调第一行直接落盘一行日志**（不经业务、不经界面）。
2. **改代码前先读原文**：按**行号 + 大括号配平**整段替换，而不是凭记忆猜锚点。（这两天我有 3 次因为跳过这步返工，教训记在案。）
3. **失败要能回滚**：构建失败脚本**自动 `git checkout` 回滚**；改完立刻提交，避免"清理工作区"时把有用的改动一起回滚掉（我因此丢过一整行测试入口，后面几轮都在点一个不存在的按钮）。
4. **自写校验脚本先自测**（好样例 + 坏样例），否则会把好文件报成坏文件。
5. **环境陷阱固化**：本机 shell 是 **Windows PowerShell 5.1** → `Set-Content -Encoding UTF8` 会带 **BOM**（污染提交标题）、`>` 重定向写 UTF-16、不支持三元 `? :`、原生程序 stderr 会污染退出码……已整理成技能条目并改用"**脚本文件 + Python 落 UTF-8 无 BOM**"的固定姿势。
