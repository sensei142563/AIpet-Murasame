# 2D → 3D 路线（2026-10-11 调研稿）

> 结论先行：**Live2D 立绘不能自动"转"成 3D**，双轨（D4）只能"另做一个 3D 的她"。
> 拿模型的最省事路线是 **VRoid Studio 手工出 VRM**（免费、直接带骨骼/表情、动漫脸好看）；
> 网站类 AI（Meshy/Tripo/Rodin 等）适合"先看形体效果"，但动漫脸与绑骨都要自己补。
> 安卓侧落地最快的渲染路线是 **WebView + three-vrm**（依赖已核实可取），
> 要长期做 AR 则上 **SceneView 2.3.0（Filament + ARCore）**。

---

## 0. 为什么不能"Live2D 转 3D"

| | Live2D | VRM |
|---|---|---|
| 资产本质 | 一张立绘切成若干**2D 网格**，靠变形器做伪 3D | glTF 2.0 的 **3D 网格 + 骨骼蒙皮** |
| 语义 | 参数驱动（眼/口/身体摆动） | humanoid 骨骼、表情、look-at、spring bone、MToon 材质 |
| 互相转换 | **不可逆**：没有 3D 拓扑信息可恢复 | 无法从 2D 网格"推"出正确拓扑 |

⇒ 规划里 `00-总体规划` 的 D4「双轨模型：Live2D 是日常形态，VRM/3D 是 AR 与实体形态」是对的：
**两套资产各自做**，不是转换关系。（参考 VRM 特性清单 <https://vrm.dev/en/vrm/vrm_features/>）

## 1. 拿到 3D 模型的三条路线（按"省事 + 可用"排序）

### 路线 A（推荐先做）：VRoid Studio 手工出 VRM
- 免费桌面工具，**导出即 VRM**：自带 humanoid 骨骼、表情（VRM Expression）、发型/服装/贴图编辑；
- 动漫脸质量**可控**，不需要重拓扑、不需要绑骨 —— 这是它相对 AI 生成的核心优势；
- 代价：需要人工捏一次（风格尽量贴丛雨：紫发、和风、刀魂气质）；
- 交付物：`pets/murasame/3d/murasame.vrm`（建议放角色包，与 ADR-002 的角色包结构一致）。

### 路线 B：网站类 AI（"听说有网站工具"说的就是这类）
- 代表：Meshy（有 VTuber 用途页 <https://www.meshy.ai/zh/use-cases/3d-avatar/vtuber>）、
  Tripo、Rodin、Hunyuan3D 在线版等；流程一般是"传图/写提示词 → 出网格 → 可选自动绑骨"。
- 优点：**几分钟出结果**，适合快速看形体、看比例，做实验成本极低；
- 缺点（社区普遍反馈，本次**未逐项验证**）：
  - 动漫脸容易"崩"（眼睛/五官不稳定）；
  - 网格面数高、拓扑乱，**绑骨与表情要另做**（自动绑骨的可用性有限）；
  - 商业使用条款、模型归属需逐条看清。
- 定位：**探路工具**，不作为最终资产来源。

### 路线 C：本地开源单图/多图生成 3D
- 代表：Hunyuan3D-2、TripoSR、InstantMesh 等（单图/少图 → 网格）；
- 优点：全本地、可批量、不吃云端额度；缺点：同样**不绑骨**、动漫脸弱、吃显存（本机 RTX 4050 6GB，注意与 F5/STT 抢显存，见 `03-架构决议` 的显存仲裁）；
- 定位：与路线 B 同档，作为"离线备选"。

**红线**（沿用 ADR-012 / `08-风险与合规`）：模型资源必须是**自产或明确许可**的，
不拷他人项目资源；Live2D SDK 与模型都另有授权约束，3D 侧同理。

## 2. 安卓端渲染 VRM 的两条技术路线（依赖已核实）

### 路线 1（最快见效）：WebView + three.js + `@pixiv/three-vrm`
- 依赖核实（2026-10-11，npm registry）：
  - `three` 最新 **0.186.1**；
  - `@pixiv/three-vrm` 最新 **3.5.5**（VRM 加载器，pixiv 官方维护，文档 <https://pixiv.github.io/three-vrm/docs/>）。
- 做法：把 three + three-vrm 打包成**本地 assets 里的 HTML/JS**（离线，不依赖 CDN），
  用 WebView 加载；Kotlin 侧只传少量指令（表情权重、看向点、相机预设、口型幅度）。
- 优点：VRM 语义（表情/look-at/spring bone）**现成可用**，开发量最小；
- 缺点：WebView 的帧率/耗电不如原生；与相机预览（CameraX）叠加时需要混合方案（WebView 透明层，参考现有 Live2D 叠加的做法：`setZOrderMediaOverlay` + TRANSLUCENT）。

### 路线 2（长期做 AR）：SceneView / Filament 原生
- 依赖核实（Maven Central）：
  - `io.github.sceneview:sceneview` **2.3.0**、`io.github.sceneview:arsceneview` **2.3.0**（Filament + ARCore 封装，含 AR 场景）；
  - `com.google.android.filament:filament-android` **1.71.5**（另有 filamat / filament-utils）。
- 优点：原生性能、直接吃 ARCore（平面检测 = 后面"识别地板"的基础）；
- 代价：Filament 不是 VRM 引擎 —— **VRM 语义层要自己写**（humanoid 映射、表情解析、look-at、spring bone、第一人称网格拆分、节点约束），MToon 只能用自定义材质**近似**并加描边 pass。
  这一结论与工程实践分析一致：<https://www.realbits.co/blog/2026-05-16-filament-backed-vrm-avatars-mobile-character-presentation>
- 取舍建议：先用路线 1 把"能动的她"跑通（快速验证体验），
  等 AR 形态需要稳定帧率与平面/遮挡时再投路线 2（可复用同一份 `.vrm` 资产，不浪费）。

> 现实检查：本机与手机仓库目前 **没有任何 VRM/glb/gltf 资产**（实测 0 个），
> 也没有任何 3D/AR 依赖（`chatter/app/build.gradle.kts` 里 0 处 filament/sceneview/arcore）。
> 所以这条线的第一步不是写渲染代码，而是**先拿到一个能动的 `.vrm`**。

## 3. 建议里程碑（无时间表，按"做完什么样"定义）

| 里程碑 | 做完长什么样 | 依赖 |
|---|---|---|
| M1 有一个能动的她 | 手机上能加载 `murasame.vrm`，能切表情、能转头看向手指点的地方 | 路线 A 产出的 VRM + 路线 1 渲染 |
| M2 站在房间里 | AR 里她站在地板上、大小正确、走近走远不飘 | ARCore 平面检测 + 路线 2（或场景锚点） |
| M3 会说话 | TTS 出声时口型同步（VRM 的 `aa/ih/ou` 表情或 BlendShape） | 现有 F5/台词包链路 + 语音时长/包络 |
| M4 被她看见 | 摄像头做人脸/身体检测，她的视线与朝向跟随（纯端侧，只发结构化结果） | 现有 CameraX + 端侧检测 |
| M5 手部互动 | 手在 AR 里能"碰"到她（射线/碰撞盒），触发动作与台词 | M2 + 碰撞盒（见下） |

**与"识别地板/碰撞箱/动捕"的衔接**（目标里的后半段）：
- **地板/碰撞箱**：ARCore 的 plane/深度本身就是地板检测；她脚下放一个碰撞盒 + 射线拾取即可做"摸头/戳一下"；
  若不用 ARCore，则走单目深度/分割（如 ML Kit / 端侧分割模型）+ 自估地面平面，精度低一档；
- **动捕**：纯视觉 2D 关键点（MediaPipe/端侧姿态模型）→ 映射到 VRM humanoid 骨骼（肩/肘/腕/髋），
  这正是 plan 里 L3「纯视觉动捕（D5 第一步）」；它天然复用 M1 的 VRM；
- **手部 AR 互动**：手部关键点（MediaPipe Hands 类）→ 指尖射线 → 与她的碰撞盒求交 → 触发动作/台词/表情。
