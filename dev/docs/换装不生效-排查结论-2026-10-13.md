# 「换装不生效」排查结论（2026-10-13）

> 起因：`tests/test_bugfix_0930b.py` 的「★ 四套衣服画出来各不相同（换装确实生效）」失败，
> 四套的不透明占比完全相同（32.61 / 37.06），看着像"换装不生效"。
> 本轮用三个递进的实验把责任分清了。**结论：产品侧解析正常，是测试那次调用的入口用错了。**

## 一、三层递进的实验与结果

| 实验 | 写法 | 结果 |
|---|---|---|
| A | 改 `data/portrait_choice.json` **顶层 `b.cloth`**（测试的写法） | 四套占比全 37.06 ⇒ 无变化 |
| B | 改 **`pets.murasame.b.cloth`** | 四套全 37.06 ⇒ 无变化（**写错了 set**：当前 set 是 `a`） |
| C | 改 **`pets.murasame.a.cloth`**（代码真正读的地方） | `load_outfit()` **正确解析出四套**：制服→校服 1952 / 睡衣→睡袍 1956 / 私服→便服 1978 / 刀服→刀装 1950 ⇒ 解析层 ✓<br>但渲染占比仍全 37.06 ✗ |

**C 是决定性的**：解析层完全正确，而渲染结果不变 ⇒ 问题在"传进渲染的图层"这一步。

## 二、根因

`classes/murasame_class.py::update_portrait(target, layers)` —— **`layers` 是调用方传进来的**：

```
5111| def update_portrait(self, target, layers):
...
5150| pixmap = self._compose_pixmap(target, layers)
```

而测试那次调用是：

```python
_pet2.update_portrait(_pet2.portrait_target, _pet2.first_portrait)
```

`first_portrait` 是**固定的初始图层表**，从头到尾没变过 ⇒ 传进去的图层不变 ⇒ 合成结果当然一样。

**所以不是产品 bug**：真实换装走的是右键菜单那条路（重新 `load_outfit()` 取到新图层 → 传进去重画）。
测试想验"换装生效"，却绕过了解析、直接喂了一个常量。

## 三、要修的是测试（并加一条更强的防线）

把测试改成"走真实入口"：
1. 写 `pets.<id>.<set>.cloth`（**代码真正读的位置**，不是顶层 `b`）；
2. 调用与右键菜单同一条路径（重新 `load_outfit()` 拿到 `cloth_id`，再交给 `update_portrait`）；
3. 期望 `load_outfit()` 的 `cloth_id` 四套**互不相同**（解析层），**并且**渲染占比至少有 3 种
   （渲染层）—— 这样两层都有断言，再出问题能立刻分清是哪一层。

## 四、顺带记录的两个"存储位置"事实（容易踩）

- `data/portrait_choice.json` 有**两种布局**：
  - 顶层 `a` / `b` / `active`：**老角色（无 `portrait.sets`）**用的；
  - `pets.<角色id>.<set>`：**有 `portrait.sets` 的角色**（murasame、芳乃等）用的。
- `murasame` 属于后者（它的 `pet.json` 里有 `portrait.sets`），所以**顶层 `a`/`b` 对它无效**。
  实测初次运行时 `pets` 分区是空的（`PET_KEYS []`），由应用自己按需创建。
- 判断走哪一套看 `tool/portrait_outfit.py::_pet_tables()`：有 `portrait.sets` 就返回表（走分区），
  否则返回 `None`（走顶层）。

---

## 五、✅ 找到真 bug 了（2026-10-13 追加，用**图像摘要**定性）

把测试改成走**真实入口** `pet._switch_cloth(名字)`（保存 → `load_outfit` → `swap_body` →
`update_portrait`，正是右键菜单点衣服走的那条路），并把渲染判据从"不透明占比"换成
**图像内容摘要**（前者太粗：实测睡衣/私服/刀服占比都恰好 31.22，会误判）：

```
解析层 cloth_id：{'制服': 1952, '睡衣': 1956, '私服': 1978, '刀服': 1950}      ← 四套全不同 ✓
渲染层 不透明占比：{'制服': 32.61, '睡衣': 31.22, '私服': 31.22, '刀服': 31.22}  ← 后三套相同
渲染层 图像摘要：  {'制服': '53c2f4fc91', '睡衣': '7ee86d5cfa',
                    '私服': '7ee86d5cfa', '刀服': '7ee86d5cfa'}                ← 后三套**像素完全相同** ✗
```

⇒ **制服 → 睡衣 确实变了；睡衣 → 私服 → 刀服 画出来的东西一模一样。**
   也就是说：**换第一次有效，之后换装不再生效** —— 这是**真的产品 bug**（用户从睡袍换便服、
   换刀装会没反应），不是我上一版结论里说的"只是测试入口用错"。上一版结论修正如下：

- **测试入口确实用错了**（写顶层 `b`、把固定 `first_portrait` 当 layers）—— 已修为真实入口；
- 修好入口之后**又暴露了真 bug**：连续换装只有第一次生效。

嫌疑点（下一轮从这里查）：`classes/murasame_class.py::_switch_cloth()`
```python
layers = getattr(self, "_last_portrait_layers", None) or self._first_portrait_for(cur_set)
layers = swap_body(layers, cur_set, _of.get("cloth_id") or 0)   # ← 怀疑这里没换掉身体层
```
第二次起 `_last_portrait_layers` 里已经是**上一件衣服的层号**，若 `swap_body` 只在
"原始身体层号"上做替换（或按已知集合匹配），就会认不出当前这件 → 原样返回 → 画面不变。

**待办**：查 `tool/portrait_outfit.py::swap_body()` 的匹配逻辑，让它能把"当前任意一件衣服的层号"
换成目标层号；补一条"连续换 3 次"的断言防回归。
