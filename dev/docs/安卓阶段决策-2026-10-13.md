## 一、结论先说：**不需要 Termux，而且"软件内置"这条路已经走完了**

手机仓 `chatter` 的 `docs/NATIVE_MIGRATION_PLAN.md` 明确记录：**Chaquopy（内嵌 Python）已被删除**，
App 现在是**纯原生 Kotlin 引擎**：

| 项 | 证据 |
|---|---|
| Chaquopy 已退役 | 该文档第 8 行："Phase 1（补原生缺口）与 Phase 2/3（**删除 Python 回退**、清理文档）已完成并提交" |
| 引擎是原生 | `NativeEngine`(Kotlin) + `PetBrain`(业务大脑) + `ChatCore.kt` / `MemoryStore.kt` / `VisionClient.kt` / `ModelConfig.kt` |
| 构建不再需要 Python | 该文档验收标准："构建只需 JDK + Android SDK"、"仓库里不再有 `.py` / `.pyc` / Chaquopy 配置" |
| 实测 | `app/build.gradle` 与根 `build.gradle` 里**没有任何** `chaquopy` / `termux` / `python` 字样 |
| 记忆格式兼容 | Kotlin 读写与 Python 完全相同的 `pets/<角色>/memory/long_history.json` + `history.json`（切换零迁移） |

⇒ **Termux 当初只是"在手机上跑 Python 后端"的临时手段**；这条路既然已经被"原生重写"取代，
Termux 探索可以直接**结案**。你想要的"自研、软件内置"= 现在这个纯 Kotlin App，**已经是了**。

**唯一还没收尾的是 Phase 4（回归验证）**：`./gradlew assembleDebug` + 真机全链路
（扫码登录 → 文字/图片/表情包收发 → 白名单 → 记忆读写 → 角色切换），并确认
`data/` 下凭据/游标/记忆文件格式不变。

## 二、3D 模型：先别急着建模（这条同意你的判断）

"建模真的难"是对的 —— 但"上 3D"不等于"自己建模"。三条路子，按成本从低到高：

| 路线 | 做法 | 成本 | 风险 |
|---|---|---|---|
| **A. 继续 Live2D（现状）** | 手机端已集成 Live2D（`docs/live2d-integration.md`），与桌宠共用"装扮即数据" | 0（已在跑） | 无 |
| **B. 用现成 VRM 模型** | VRM 是通用 3D 人形格式，安卓有现成渲染方案（例如 Play 上的 [ISD Studio 3D/VRM](https://play.google.com/store/apps/details?id=com.lilysoftllc.isdstudio3dtrial)），或 Unity + UniVRM | 中：要接渲染器 + 表情/骨骼驱动 | 找到**可商用**的模型不好找；风格要与现有角色统一 |
| **C. 自己/外包建模** | 从头做角色网格 + 绑定 + 表情 | 高 | 周期长、返工多 |

**建议**：先用 **B 做一次"能不能跑起来"的技术验证**（拿一个免费可商用的 VRM 在安卓上渲染、
驱动眨眼与口型），跑通了再谈"要不要把主角色换成 3D"。**别在验证之前投入建模成本。**

## 三、3D AR：**安卓有，只是不叫 ARKit**

你看到的"基于 iPhone 生态"是 **ARKit**（苹果专用）。安卓的对应物是 **ARCore**，
官方提供 Android(Java/Kotlin) 快速开始：[Quickstart for Android | ARCore](https://developers.google.cn/ar/develop/java/quickstart)。
Live2D 官方平台支持列表里 Android 也在（[Cubism SDK 平台支持](https://docs.live2d.com/zh-CHS/cubism-sdk-manual/platform/)）。

所以"3D AR 只有 iPhone"这个判断**需要修正**：安卓要么用 **ARCore 原生**，
要么用 **Unity + ARCore**（社区教程很多）。区别只在：
- 覆盖面：ARCore 需要设备支持（中高端机型基本都有，需按机型核对）；
- 工作量：原生 ARCore 要自己写平面识别 + 光照估计；Unity 路线省事但包体大。

**建议**：AR 放在**远期**（PPT 里也是这么排的），先用 ARCore 的 HelloAR 样例做一次
"在桌面上放一个模型"的可行性验证，再决定是否投入。

## 四、互动（手部 / 视线 / 动作识别）：手机上要换方案

| 能力 | PC 侧（现在/可做） | 手机侧建议 |
|---|---|---|
| 手部检测 → 她看着我的手 | 摄像头链路已通，可接手部关键点检测 | MediaPipe 系列在 Android 有官方支持，**需按机型实测功耗与帧率**（待核） |
| 识别"捏脸"等动作 | 可用关键点 + 时序判定 | 同上；手机上更依赖前摄，注意发热 |
| 视线跟随 | 眼动/头姿驱动 Live2D 参数 | Live2D 参数驱动与 PC 一致（同一套模型参数） |

**共性做法**：把"识别"与"表现"分开 —— 识别侧只输出**少量标准参数**
（例如 手位置/捏合程度/头姿角度），表现侧由 Live2D/3D 去消费。
这样 PC 与手机可以**共用同一套表现逻辑**，识别侧各自实现。

## 五、毫米波动捕：迁移路线

已确认可复用的前提：课题组另有一套动作识别装置（面向临床动作分析），课题结束后可迁移其参数流。

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 1 | 把装置的输出对接成**标准参数流**（不吃原始点云，只要"姿态/动作"结果） | 一个稳定的参数接口 |
| 2 | 在 PC 侧先用它驱动桌宠（哪怕只是"转头看你"） | 验证"雷达 → 表现"这条链 |
| 3 | 需要时再往手机侧搬（若装置不便携，也可只做"PC 侧高级配件"） | 按实际便携性决定 |

**为什么不急**：它依赖课题进度，而且**雷达的优势是隐私与全天可用**（不依赖光线），
适合当"PC 侧的高级传感器"，不是手机端的必选项。

## 六、建议的执行顺序（安卓段）

1. **收尾 Phase 4 回归**（构建 + 真机全链路），把"纯原生"这件事**验收掉**；
2. 把 Live2D 在手机上的**表现对齐 PC**（换装/表情/口型）；
3. 做 VRM 渲染的**技术验证**（只验证，不建模）；
4. 用 ARCore 样例做**一次 AR 可行性验证**；
5. 互动（手部/视线）选一个最小闭环（例如"她看着我的手"）在手机上前摄跑通；
6. 毫米波按课题进度另线推进。

> 结论一句话：**Termux 不用；3D 先验证别建模；AR 安卓用 ARCore；互动把"识别"与"表现"解耦。**
