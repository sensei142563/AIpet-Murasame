## 0. 结论摘要（先看这 12 条）

1. **不要引入 Mem0/Zep/Letta 作为运行时**。它们是「记忆层/Agent 运行时」，而你的三个代码库已经有自己的 LLM 调用、人格 prompt、检索逻辑。引入 = 重写编排层。正确做法是**抄它们的架构模式，不抄它们的部署**。Mem0 是「插件式记忆层」，Letta 是「Agent 运行时」，两者哲学不同且 Letta 锁定性强（[Mem0 vs Letta 对比](https://vectorize.io/articles/mem0-vs-letta)）。
2. **统一抽象是「事件日志 + 物化视图」**，不是「一个大 JSON」。`history.json`/`long_history.json` 这种整文件读写必须退化为导出格式，不是主存储。
3. **冲突解决推荐 LWW-per-field + HLC（混合逻辑时钟）+ append-only 事件日志**，**不要**上 Automerge/Yjs 全量 CRDT。理由见 §3.2：你的数据形态是「日志 + 少量单值状态」，不是「多人协同富文本文档」。
4. **隐私是第一等公民，不是事后补丁**。记忆从写入那一刻就带 `privacy` 标签（`local`/`device`/`lan`/`sync`/`public`），同步层默认拒绝未标注记忆出设备。
5. **合规上有重大利好**：《个人信息保护法》第七十二条明确「自然人因个人或者家庭事务处理个人信息的，不适用本法」（[PIPL 全文](https://www.hbrd.gov.cn/system/2026/09/11/102222071.shtml)）。你自己 + 家人的桌宠目前**不在 PIPL 管辖范围**；一旦开放给陌生人使用（哪怕免费），立刻落入管辖，第 28/29/38/39 条全部生效。
6. **嵌入模型分三档**：云端质量档 `Conan-embedding-v2`（1.4B，MTEB 中文 74.24 / 英文 73.52，2025-05-19 SOTA，[论文](https://ar5iv.labs.arxiv.org/html/2509.12892)）；自建/中档 `bge-m3`（569M，1024 维，8192 token，dense+sparse+ColBERT，[官方文档](https://bge-model.com/bge/bge_m3.html)）；端侧 `EmbeddingGemma`（308M，768→128 维 MRL，2K context，量化后 <200MB RAM，[发布博客](https://developers.googleblog.com/es/introducing-embeddinggemma/)）。
7. **Codebase C 的 `MemorySearch.kt` 已经用了 RRF，公式 `1/(60+rank)` 是标准实现**，方向正确，**可作参考**（ADR-003：`live2D` 只读参考，思路可借、文件不可拷）。它缺的是**重排层**——`recency`（时间衰减）+ `importance`（重要性）+ MMR 去重；**这一层不是"第三路召回"**（三路召回 = 语义向量 / 关键词 BM25 / 结构化精确匹配，见 §4.2）。
8. **`learned.json` 的 `working` / `profile` / `episodes` / `topic_ideas` 字段并不是空壳**：A 线**已有基础实现**——`tool/self_learn.py:316 memory_note()` 做分层召回（关键词命中 +1.5 / fact +0.4 / 时间权重），读 `working/profile/episodes/日记`，并由 `tool/chat.py:166-171`、`tool/cloud_API_chat.py:139-145` **每轮注入**。缺的是更细的机制（时间衰减、重要性、去重）。所以本次改造的定位是**增强**，不是"从零填坑"。
9. **事件总线用 MQTT 语义 + 自研 WebSocket hub**，topic 命名 `pet/{pet_id}/{domain}/{entity}/{action}`，8 个 domain 固定词表。
10. **落地必须分三步**，且第一步（文件夹 + 单文件记忆库 + 手动导出导入）就应该能跑通「桌面 ↔ 手机记忆互通」，否则第三步永远到不了。
11. **最大的技术风险不是同步，是记忆污染**：LLM 幻觉被写进长期记忆后会自我强化。必须「候选 → 验证 → 生效」两阶段写入 + 强制 `source_event_ids`。
12. **不要做的反模式**：把整段对话塞进长期记忆；让 LLM 直接覆盖人格文件；无上限 append 向量；多设备各自跑一份人格摘要然后互相同步。

### 1.2 关键取舍：RAG vs Agentic Memory

- **RAG 是「检索文档」**，记忆是「检索经历」。区别在于：文档不会因为你今天问了它而变化；记忆会因为你今天做了什么而变化，而且**需要遗忘、需要失效、需要冲突解决**。
- Mem0 论文给出的量化理由很硬：相对「把全部对话历史塞进 context」的 full-context 方案，Mem0 **p95 延迟低 91%，token 成本省 90%+**，同时在 LOCOMO 上四类问题（单跳/时间/多跳/开放域）全面胜出，LLM-as-a-Judge 相对 OpenAI 基线 +26%（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)）。
- 但 Mem0 也有短板：一项独立评测给出 **LongMemEval 49.0%**，且「既不用多策略检索也不用 cross-encoder 重排」（[对比文章](https://vectorize.io/articles/mem0-vs-letta)）。Zep 在 DMR 上 94.8% vs MemGPT 93.4%，LongMemEval 准确率最多 +18.5%、延迟 -90%（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)）。
- **对桌宠的结论**：记忆系统 = RAG（粗召回）+ 结构化状态（精确）+ 反思层（把情节压成语义）。纯 RAG 会退化成「翻聊天记录」，纯结构化会退化成「没有温度的数据库」。

## 2. 记忆分层设计

### 2.1 分层总览

| 层 | 名称 | 存什么 | 写入时机 | 读取时机 | 保留期 | 衰减/遗忘 |
|---|---|---|---|---|---|---|
| L0 | 工作记忆 working | 当前会话的原始轮次、当前任务栈、临时变量 | 每轮 | 每轮必带 | 会话生命周期 | 会话结束即丢（可选择性提升到 L1） |
| L1 | 情节记忆 episodic | 事件（谁、何时、何地、做了什么、情绪效价） | 事件发生即时 | 检索召回 | 热 30 天 / 冷 365 天 | 30 天后降级为摘要，原事件转冷存；访问可复活 |
| L2 | 语义记忆 semantic | 关于用户/世界的事实三元组（含置信度与有效期） | 反思时从 L1 蒸馏 | 高置信直插 prompt | 永久 | 矛盾时 `superseded`，不删除；低置信长期未验证则 `disputed` |
| L3 | 程序性记忆 procedural | 习惯（几点上线、常用 app）、口头禅、语气规则、行为策略 | 统计聚合 / 人工固化 | 每次构建 prompt | 永久 | 慢更新（EWMA），只在样本 ≥ N 时改 |
| L4 | 情感状态 affect | mood / affinity / boredom / social / energy / 欲望 | 每轮或每次互动 | 每轮必带 | 当前值 + 7 天曲线 | EWMA + 向基线回归 |
| L5 | 用户画像 profile | 槽位化档案：称呼、作息、专业、饮食偏好、雷区、纪念日 | 抽取后缓冲 | 每轮必带（压缩版） | 永久 | 覆盖写，保留 `previous_value` 历史 |
| L6 | 关系亲密度 relationship | 亲密度、关系等级、里程碑事件、称呼演化 | 里程碑触发 | 每轮必带（一行） | 永久 | 单调缓增；重大负面事件可下调（需人工确认） |
| L7 | 日记与反思 diary & reflection | 日记（角色第一人称）、反思笔记（带链接的洞见） | 每日定时 / 重要度累积触发 | 检索 + 日记回顾 | 永久 | 不衰减；反思可被后续反思覆盖（保留链条） |

### 2.2 各层详解

**L0 工作记忆**：不写盘（或临时 `runtime/session.json` 供崩溃恢复）；直接进 messages 数组；不参与人格拼接。**硬约束：主动问候不能进对话历史**——`live2D`（参考实现）的做法是用独立的 `ChatMessage.greeting()` 角色写入、构建历史时过滤（`live2D/.../ai/AutonomyEngine.kt:194-195`）；**本项目（含 `chatter`）尚未实现，属于待补项**，照"问候不进历史"这个原则自己实现即可。

**L1 情节记忆**：**只写事件，不写对话全文**。一条事件 = 一次可被感知的变化（用户说话、被摸头、摄像头识别到写作业、机械臂完成抓取）。每条必须有 `salience ∈ [0,1]`，来源三选一：规则表（被摸头 = 0.4）、LLM 打分（Generative Agents 的 1–10，映射到 0–1）、用户显式反馈（= 1.0）。读：多路召回（§4）。保留：热 30 天，之后由反思压缩进 L2/L7，原事件 `archived`，只在用户追问细节时回捞。遗忘 = **降权不删除**；真删除只由用户发起（PIPL 第 47 条）。

**L2 语义记忆**：结构 `(subject, predicate, object, confidence, valid_from, valid_to, status, source_event_ids[])`。写：反思任务从 L1 蒸馏，**每条事实必须挂 ≥1 个 `source_event_id`，否则拒写**（防幻觉硬闸门）。冲突：旧事实 `valid_to = now` + `status='superseded'`，新事实 `supersedes=old_id`，**不物理删除**——「以前喜欢辣、现在不喜欢」本身是有价值的记忆。读：`confidence ≥ 0.8 && status='active'` 直插 prompt；`0.5–0.8` 进候选池。

**L3 程序性记忆**：三类——`habits`（作息/app/上线时段分布）、`style`（口头禅、句长、语气、称呼）、`policy`（何时不打扰、何时主动开口）。`habits` 由本地统计任务每小时更新（现有 `habits.json` 的 `hours`/`apps` 已有雏形，且 `tool/habits.py:212-233` **已在算每日 first/last 时间窗与平均起床/最晚时间**、`:186` 已有活跃时段分段；**缺的是 EWMA 与样本门槛**）；`style`/`policy` 人写为主。**铁律：人格锚点（`prompt.txt`/`longtext_prompt.txt` 核心人设）禁止 LLM 自动改写**，LLM 只能往 `candidates` 追加建议、由你审核合并。

**L4 情感状态**：`{mood, affinity, boredom, social, energy, valence, ts}` + 7 天环形缓冲。写：`v ← α·v_new + (1−α)·v_old`，`α = 0.05 + 0.25·salience`。衰减：无事件时向基线回归 `v ← v + (v_baseline − v)·(1 − exp(−Δt/τ))`，τ ≈ 6h。读：**每轮必带，且必须转成语气指令**，不是把数字塞进 prompt。同步：最难同步的一层，用「只同步事件、各端本地重算」（§3.2），允许 ±5% 差异。

**L5 用户画像**：槽位化（借 Memobase）`topic/subtopic = value`，如 `identity/name`、`study/major`、`food/spicy`、`schedule/wake`、`taboo/topics`。写：抽取 → 入 `profile_buffer`（不立即生效）→ 定时 flush，flush 时做冲突检测 + 证据检查。读：压成「【已知用户信息】」块。永久保留，每次覆盖留 `previous_value` + `source_event_id`。

**L6 关系亲密度**：`{affinity: 0..100, level: 陌生/熟悉/亲近/挚友, milestones[], address_style}`。只由里程碑事件 + 每日互动统计驱动，**不允许 LLM 自由增减**（防「聊几句就变挚友」）。读：一行摘要注入（`care.json` 的 `days` 已在做类似的事）。

**L7 日记与反思**：日记已有实现（A 的 `learned.json.diary`、C 的 `diaries` 表），保持第一人称角色视角。反思抄 A-MEM 笔记结构 `{content, keywords[], tags[], context_desc, links[], embedding}`，但**要有情绪色彩与主观视角**（「主人最近总在半夜写代码，本座有点担心」），不是中立摘要。触发：`Σ salience(未反思事件) > 阈值` 或每日定时。

```json
  "schema_ver": 1
}
```

字段约束：
- `event_id`：ULID（时间有序，全局唯一，不依赖自增，天然适合多设备）。
- `hlc`：Hybrid Logical Clock，`{物理毫秒}-{逻辑计数}-{设备ID}`，用于冲突判因果。CRDT 生态普遍用 HLC 而非纯墙钟（[CRDT 对比](https://mvpfactory.io/blog/crdts-for-offline-first-mobile-sync-automerge-vs-yjs-merge-semantics-and-the/)）。
- `privacy`：`local | device | lan | sync | public`，默认 `local`。

## 3. 多设备同步架构

### 3.1 三种拓扑对比

| 维度 | ① 云为中心 | ② 局域网 P2P 同步 | ③ 混合（推荐终局） |
|---|---|---|---|
| 拓扑 | 所有设备连云端 API | 同一 WiFi 下设备互连（mDNS 发现 + WebSocket/gRPC 直连） | 局域网优先；不在同一网时降级到云中继 |
| 离线能力 | 需本地缓存 + 重放 | 强（局域网内不依赖外网） | 强 |
| 实现成本 | 中（但要写服务端 + 账号 + 鉴权 + 备份） | 中高（发现、NAT/防火墙、多对多状态、无中心时钟） | 高 |
| 隐私 | 最差（记忆必须出设备） | 最好（记忆不出局域网） | 可控（`privacy` 标签决定走去哪条路） |
| 机器人头/机械臂/智能家居接入 | 简单（都是 HTTP 客户端） | 简单（MQTT broker 在局域网内） | 简单 |
| 手机在外网时 | 天然可用 | **不可用**（这是致命伤） | 可用（走云中继） |
| 运维 | 服务器 + 域名 + 证书 + 备份 | 几乎为零 | 服务器 + 局域网 broker |
| 适合阶段 | 第三步 | 第二步（同时） | 第二步末 → 第三步 |

**结论**：不要二选一。核心是**一条能切换传输层的同步协议**，拓扑只是它的实现。设备在同一局域网时走 `--lan`（延迟低、隐私好），不在时走 `--cloud`。这对「学生 + 手机带出门 + 家里机器人」的场景是唯一合理解。

### 3.2 冲突解决：推荐方案

| 策略 | 适用字段 | 举例 | 评价 |
|---|---|---|---|
| **LWW-per-field + HLC** | 绝大多数：画像槽位、事实的 `confidence`/有效期、程序性配置 | `food/spicy` 两设备同时改 | **主方案**。按字段粒度而非行粒度，避免「A 改名字、B 改口味」互相覆盖 |
| **append-only 事件日志（无需冲突解决）** | `mem_event`、`mem_milestone` | 所有原始事件 | **最省心**：事件只追加，永不冲突。冲突只发生在「物化视图」上 |
| **G-counter / 求和** | 互动次数、`days`、`samples` | 两端各记了 5 次触摸 | 用 CRDT 计数器，合并 = 求和；这是真 CRDT，值得用 |
| **EWMA 重算（不合并状态，合并输入）** | `mem_affect` | mood/affinity | **推荐**：只同步影响情绪的事件，各设备用同一套公式在本地重算。允许 ±5% 漂移，比强行合并更好（且符合「不同终端对情绪感受略有不同」的产品直觉） |
| **版本向量** | 不需要 | — | 复杂度高（要为每个 device × entity 维护计数），在你这个规模（1 用户、<10 设备）收益为负 |
| **全量 CRDT（Automerge/Yjs/cr-sqlite）** | 不需要 | — | Automerge 富文档模型（堆内存 8–12MB/10K ops）、Yjs 实时文本（3–5MB）、cr-sqlite 行级（2–4MB、SQLite 原生）；**你的数据不是协同文档**，强行套用会付出 compaction 和 FFI 的代价（[CRDT 对比](https://mvpfactory.io/blog/crdts-for-offline-first-mobile-sync-automerge-vs-yjs-merge-semantics-and-the/)） |
| **人工冲突 UI** | 极少数 | 两条互斥的高置信事实 | 只在 `confidence` 都 ≥0.9 且逻辑互斥时弹出确认 |

**最终推荐**：
```
事件层（mem_event / mem_milestone）  →  append-only，ULID + HLC 排序，无需冲突解决
计数层（days / samples / 互动次数）  →  G-Counter，求和合并
状态层（affect）                     →  事件重放 + 本地重算，容忍漂移
单值层（profile/fact/relationship）  →  LWW-per-field + HLC，tie-break = device_id 字典序
删除                                →  tombstone（`status='deleted'` + `deleted_at`），比 CRDT 的删除更可控，也满足 PIPL 第 47 条
```

### 3.3 离线优先

规则：
1. **所有写操作先写本地**，立即返回成功，生成 `sync_oplog` 条目。
2. `mem_event` 的 `embedding` 在本地算（端侧模型），**不上传向量**，只上传文本（省带宽、也避免向量泄漏语义）。接收端自行重算向量。
3. 冲突窗口：HLC 保证因果；本地墙钟只用于展示（`ts_local`），不用于排序。
4. 网络恢复后按 `sync_cursor` 增量拉取：`GET /sync/pull?since_op=<op_id>&limit=500`。
5. 每次同步后本地重跑「反思/衰减」任务（幂等）。

### 3.4 传输选型

| 用途 | 选型 | 理由 |
|---|---|---|
| 增量同步（拉/推） | **REST/JSON + 游标分页** | 简单、可缓存、可在任何语言实现（Python/Kotlin 都零成本）；批量上传用 `POST /sync/push` 数组 |
| 实时事件（「当下发生了什么」） | **WebSocket**（云/局域网 hub）；局域网可换 **MQTT** | 事件是低延迟小消息，HTTP 轮询不合适；MQTT 的 topic + `+`/`#` 通配符天然匹配订阅需求（[MQTT topic 规范](https://cloud.tencent.cn/developer/article/2562223)） |
| 大文件（语音、图片、模型） | 独立对象存储 / 局域网 HTTP 直传 | 不要塞进同步协议 |
| gRPC | **不推荐** | 客户端是 Python + Kotlin + 单片机，gRPC 在嵌入式侧成本高于收益；REST + WS 覆盖面更好 |
| 局域网发现 | mDNS (`_aipet._tcp`) | 零配置；Android 有 NsdManager，Python 有 zeroconf |
| 设备→设备直连 | WebSocket 直连（同一 broker/hub 亦可） | 避免引入额外 P2P 打洞复杂度 |

### 3.5 加密与隐私（中国合规）

**法律现状（已核验全文）**：
- **PIPL 第七十二条**：「自然人因个人或者家庭事务处理个人信息的，不适用本法。」（[PIPL 全文](https://www.hbrd.gov.cn/system/2026/09/11/102222071.shtml)）→ **你自己 + 家人使用的桌宠不在 PIPL 管辖内**。这是本项目最大的合规红利。
- **一旦对外提供**（应用商店、公开服务、给别人用），以下全部生效：
  - 第 28 条：**生物识别、行踪轨迹**属敏感个人信息 → 手机摄像头人脸、位置、语音声纹都算。
  - 第 29 条：处理敏感个人信息须**单独同意**（不能混在总协议里）。
  - 第 24 条：自动化决策须保证透明度与公平，推送/营销须提供「不针对个人特征」的选项或便捷拒绝方式。
  - 第 19 条：保存期限应为「实现处理目的所必要的最短时间」→ 你的「永久保留」策略需要给出理由或引入用户可控的保留期。
  - 第 47 条：目的实现 / 撤回同意 / 保存期满 → **必须删除**。所以必须有真正的删除路径（tombstone → 物理清除）。
  - 第 8 条：个人信息质量义务 → **正好是「防幻觉写入长期记忆」的法定理由**。
  - 第 38/39 条：出境需安全评估 / 认证 / 标准合同三选一 + 单独同意（[个人信息出境标准合同办法](https://www.gov.cn/zhengce/202311/content_6917770.htm)）。
  - 第 55 条：处理敏感个人信息、自动化决策、向境外提供 → **事前个人信息保护影响评估（PIA）**，报告保存 ≥3 年。
- **现实风险点**：调用 DeepSeek/Qwen 云端 LLM 本身就把记忆内容传给了第三方（若服务器在境内，不构成「出境」，但仍是「向其他处理者提供」，触发第 23 条 + 单独同意）。若换成 OpenAI/Anthropic/Gemini，服务器在境外 → 触发第 38/39 条。**建议：这条在实现里做成可配置项，默认只用境内 API**（未验证：具体 API 的服务器地域需各自核实服务条款）。

**加密设计**：
| 层 | 措施 |
|---|---|
| 传输 | TLS 1.3（局域网自签证书 + 首次信任指纹固定） |
| 静态（设备） | Android：`EncryptedFile`/Keystore 包裹数据库密钥；桌面：SQLCipher 或 OS keyring 派生的密钥 |
| 静态（云） | **服务端零知识**：记忆包在上传前用设备主密钥对称加密（XChaCha20-Poly1305），服务端只存密文 + 索引元数据 |
| 密钥分发 | 一台设备作为「主设备」生成主密钥，通过局域网扫码 + QR 一次性传输给其它设备；云端只存密钥的 passphrase 包裹版本（Argon2id） |
| 服务端可检索性 | 若服务端需要向量检索，则只能对**标注为 `sync` 且允许服务端解密**的记忆做（需额外一层服务端密钥）——这也是为什么默认 `local` |
| 不可信设备撤销 | 设备列表 + 密钥轮换（重加密全部记忆包）。代价高，所以设备数应保持在个位数 |

> 注意：**「服务端零知识」与「服务端向量检索」本质冲突**。务实做法：服务端只做**加密转发 + 盲存储**，检索全部在端上做（端侧向量索引 + 同步全量加密包）。以你的数据量（一年几千条记忆 ≈ 几 MB），**端侧全量检索完全可行**，这是本设计最关键的简化。

### 3.6 记忆可见性开关

五级，默认最严：

| 级别 | 含义 | 允许离开设备？ | 典型内容 |
|---|---|---|---|
| `local` | 只在产生它的设备上 | ❌ | 摄像头原始帧、声纹、密码、具体位置坐标 |
| `device` | 只在该用户自己的设备族内（含手机↔桌面直连） | 仅局域网 | 触摸互动、心情波动、习惯统计 |
| `lan` | 局域网内可广播给机器人/家居 | 局域网内 | 「用户在写作业」这类当下情境 |
| `sync` | 可上云同步 | ✅ | 画像槽位、日记、反思、长期事实 |
| `public` | 可导出/分享/用于评测 | ✅ | 用户显式标记的内容 |

实现要点：
1. `privacy` 在**写入时**由事件类型规则表决定，不由 LLM 决定（LLM 会误判）。
2. 同步层有**强制闸门**：`if (item.privacy not in allowed_for_this_transport) drop and log`。默认拒绝。
3. 用户可见的开关面板：按**层**和**类型**两个维度开关，不是按单条（单条开关太啰嗦）。但提供「查看/删除单条」。
4. 提供 **「记忆审计日志」**：哪些记忆出过设备、什么时候、去了哪。这既是隐私权利，也是你自己的调试工具。

### 4.2 混合检索

三路召回 → RRF 融合 → （可选）rerank → 时间衰减/重要性重排 → MMR 去重。

> **术语约定（避免 §4.2 与 §0.7 的口径打架）**
> - **三路召回** = ① 语义向量（dense）② 关键词精确匹配（BM25/sparse）③ **结构化精确匹配**（直接查 `mem_fact`/`mem_profile_slot`）。
> - **重排层** = 时间衰减（`recency`）+ 重要性（`importance`）+ MMR 去重。**它不是"第三路"，也不属于召回。**
> 下文旧文中出现的"第三路信号"一律按此约定理解。

Codebase C 的 `MemorySearch.kt` 已经实现了两路（BM25 + 余弦）RRF，`1/(60+rank)` 是标准形式：

```
RRF(d) = Σ_r  1 / (k + rank_r(d)),   k = 60
```

**必须补的东西**（①②属**召回**，③④属**重排**）：

1. **补上三路召回里缺的那一路：结构化精确匹配**。查询里出现"我妈妈"时，直接查 `mem_fact(subject='user.妈妈')`，这类命中不该靠向量。
2. **BM25 的 IDF 不能省**。Codebase C 的注释写「忽略 IDF，语料小，简化」——在几百条记忆时确实无感，但记忆量到 5000+ 时，高频词（"主人""本座"）会主导 BM25 排名，必须补 IDF。
3. **中文分词**：BM25 依赖分词质量。建议 `jieba`（Python）/ `SmartCN` 或 `mmseg`（Android，未验证最优选择）；若上 sparse 向量（bge-m3 自带 lexical weights），可绕过分词。
4. **重排层**：`recency`（时间衰减）+ `importance`（重要性）+ MMR 去重，公式见 §4.3。**它不属于召回，也不要叫"第三路"。**

### 4.3 打分公式

综合 Generative Agents 的三因子与 RRF：

```
# 第一段：召回融合
rrf(d) = Σ_{r ∈ {bm25, dense, sparse, exact}} 1 / (60 + rank_r(d))

# 第二段：记忆因子（各自 min-max 归一化到 [0,1]）
recency(d)    = 0.5 ^ (Δh(d) / H)          # Δh = 距上次访问的小时数，H = 半衰期（默认 168h）
importance(d) = salience(d)                 # 写入时的 0..1
relevance(d)  = cos(e_q, e_d)               # 归一化向量点积

# 第三段：权重（陪伴场景建议值，可按角色调）
score(d) = 0.45·relevance(d) + 0.25·importance(d) + 0.15·recency(d) + 0.15·rrf_norm(d)

# 第四段：硬过滤（在打分之前）
filter: privacy 允许  &&  status != 'deleted'  &&  (pet_id 匹配) && (valid_to is null or valid_to > now)

# 第五段：MMR 去重（避免 5 条"被摸头"占满预算）
MMR = argmax_{d ∉ S} [ λ·score(d) − (1−λ)·max_{s ∈ S} sim(d, s) ]，λ = 0.7
```

**访问即强化**：被检索到的记忆 `last_access_ts` 更新 → `recency` 回升。这是 Generative Agents 里 recency 用「最近**访问**时间」而非创建时间的原因（[原论文 §4.1](https://ar5iv.labs.arxiv.org/html/2304.03442v1)），也让记忆有「越用越清晰」的性质。

**为什么权重这样分配**：陪伴场景里「相关内容」永远比「最近」重要；但 `importance` 权重不能太低，否则「用户说过想自杀」这种高重要度低频记忆会被埋掉。`recency` 给 0.15 是防「永远只想起同一件事」。

### 4.4 上下文预算分配

按 8K token 预算（DeepSeek 上下文是 1M，但**成本随输入线性增长**，且长 context 会稀释注意力）：

| 区块 | token | 占比 | 内容 | 可压缩性 |
|---|---|---|---|---|
| System / 人格骨架 | 900–1400 | ~17% | 角色核心设定、语气规则、输出格式约束 | 不可压缩，**永远缓存** |
| 程序性记忆（style/policy） | 150–300 | ~4% | 口头禅、称呼、当前不打扰策略 | 固定模板 |
| 情感状态 | 50–100 | ~1% | 「心情 85/100，亲密度 83，略困」 | 数值 → 自然语言 |
| 关系摘要 | 30–50 | <1% | 「认识 101 天，亲近」 | 一行 |
| 用户画像（压缩） | 200–400 | ~5% | 【已知用户信息】槽位列表 | 按相关度裁剪 |
| **检索到的记忆** | **800–1500** | **~20%** | L1 事件 + L2 事实 + L7 反思，按 score 降序填充 | 动态 |
| 对话历史 | 2000–3500 | ~42% | 最近 N 轮（`live2D` 参考实现里有"30 分钟断点"这一类做法，**本项目尚未实现**，待核验其确切口径） | 超长时摘要 |
| 工具结果 | 500–1500 | ~15% | 搜索/天气/日程 | 只在触发轮注入 |
| **预留** | **400** | **~5%** | 输出长度 + 意外 | — |

规则：
- 检索记忆按 score 降序填，**填到预算 90% 就停**，留余量。
- 每条记忆注入时带**轻量来源标记**（`[9月30日]`），让模型能表达「我记得前几天……」而不是「根据我的数据库」。
- **记忆条目要被改写为自然语言**再注入，而不是塞 JSON。JSON 进 prompt 会显著增加幻觉与格式模仿（这一点在「Agent 输出 JSON」的已知现象里很常见）。
- 主动问候轮（无用户输入）：预算压到 4K，全部给记忆和人格。

## 5. 跨模块事件总线（关键设计）

### 5.1 统一事件模型

```typescript
interface PetEvent {
  event_id:   string;      // ULID，时间有序、全局唯一
  hlc:        string;      // 混合逻辑时钟，冲突判因果
  ts_utc:     number;      // 事件发生时间（毫秒）
  ts_local:   string;      // 本地墙钟 'YYYY-MM-DD HH:MM:SS'（展示用）
  source:     DeviceKind;  // desktop|phone|robot_head|arm|iot|qq|wechat|vm
  device_id:  string;
  pet_id:     string;      // 多角色共存时区分
  type:       string;      // 见 §5.2 词表
  actor:      'user'|'pet'|'device'|'system'|'third_party';
  subject?:   string;      // 'pet.murasame' | 'user' | 'env.living_room'
  payload:    Record<string, unknown>;
  salience:   number;      // 0..1，驱动「值不值得记 / 值不值得说」
  valence:    number;      // -1..1，情绪效价
  privacy:    'local'|'device'|'lan'|'sync'|'public';
  ttl_ms?:    number;      // 若为「状态型」事件（如"在写作业"），多久后自动失效
  trace_id?:  string;      // 因果链：谁触发了谁
  causation_id?: string;   // 直接父事件
  schema_ver: number;
}
```

**关键设计点**：
- `ttl_ms` 是**状态型事件**的核心。不是「发一个 study=true 事件」，而是「发一个 30 分钟后自动失效的 study=true」。这样「用户不写作业了」不需要显式事件——**缺失即失效**（类似 Home Assistant 里 sensor 变 unavailable）。这消掉了一大类状态同步 bug。
- `trace_id` + `causation_id` 让「手机看到写作业 → 桌宠说话 → 机器人头表情」这条链可追踪、可调试、可做因果回放（改一条规则就能重放验证）。
- `salience` 同时驱动三件事：记忆写入阈值、是否打断用户、是否广播到全设备。**一个字段，三种用途**，这是这套设计最省事的地方。

参考：Home Assistant 的 `EventBus` 用「事件类型 → 监听器列表」的字典做 O(1) 分发，并有 `MATCH_ALL` 特殊键让监听器收全部事件（[HA 事件系统](https://mintlify.wiki/home-assistant/core/architecture/event-system)）。这个结构直接可用。MQTT 的消息系统综述也可参考 IETF 的 agentic AI 消息传递草案（[IETF draft](https://www.ietf.org/archive/id/draft-mpsb-agntcy-messaging-00.html)）。

### 5.2 Topic 命名规范

```
pet/{pet_id}/{domain}/{entity}/{action}[:{qualifier}]
```

固定 8 个 domain（**闭合词表**，不允许新增，需要时用 entity 扩展）：

| domain | 含义 | 例子 |
|---|---|---|
| `sense` | 原始感知（尽量端侧处理后再发） | `pet/murasame/sense/phone/visual.activity` |
| `context` | 融合后的情境判断（多个 sense 的结论） | `pet/murasame/context/user.state` |
| `affect` | 情感/欲望状态变化 | `pet/murasame/affect/mood.changed` |
| `memory` | 记忆写入/检索事件 | `pet/murasame/memory/fact.created` |
| `act` | 请求某终端执行输出 | `pet/murasame/act/speech.request` |
| `ctrl` | 控制/抑制其它终端的行为 | `pet/murasame/ctrl/arm.suppress` |
| `env` | 环境设备状态/指令 | `pet/murasame/env/home/light.set` |
| `sys` | 系统：心跳、设备上下线、错误 | `pet/murasame/sys/device.online` |

订阅通配符沿用 MQTT 语义：`+` 匹配一级，`#` 匹配多级（[MQTT topic 规范](https://cloud.tencent.cn/developer/article/2562223)）。

约束：
- **全小写**，`snake_case` 用于多词（`visual.activity` 里的点保留给「实体.动作」）。
- topic **本身不携带数据**（不用 `pet/x/env/light/on` 这种），数据一律在 payload。
- topic 只表达「什么类别的变化」，**不表达严重程度**（严重程度 = `salience`，在 payload 里）。

### 5.3 订阅与路由机制

三层路由，逐层收窄：

```
① 静态订阅表（设备能力声明）
   robot_head 订阅: pet/{id}/affect/#, pet/{id}/act/expression.*, pet/{id}/context/#
   arm        订阅: pet/{id}/ctrl/#, pet/{id}/context/user.state
   iot        订阅: pet/{id}/env/#, pet/{id}/context/user.state
   desktop    订阅: pet/{id}/#,  (但受 salience 门限)
   phone      订阅: pet/{id}/affect/#, pet/{id}/act/speech.*

② 注意力门限（每设备可配）
   设备收到事件后，若 payload.salience < device.min_salience → 丢弃
   desktop 默认 0.2 / robot_head 0.3 / iot 0.5（家居设备不该被小事打扰）

③ 抑制策略（"不打扰"的实现）
   pet/{id}/ctrl/arm.suppress  { "until": ..., "reason": "user.study" }
   机械臂收到后进入静默；`user.state` 变为 idle 时自动解除（ttl 机制）
```

**"不打扰"必须是显式的 `ctrl` 事件**，而不是各设备自己去猜状态。这样：
- 抑制有明确的开始和结束；
- 可以审计「今天为什么机械臂一整天没动」；
- 新增设备只要订阅 `ctrl/#` 就自动继承整套礼貌规则。

### 5.4 端到端示例：「手机摄像头看到你在写作业」

**触发链**

```
[phone] 端侧视觉分类器（不上传图像！）
  → publish pet/murasame/sense/phone/visual.activity
    { "activity":"study", "confidence":0.82, "objects":["作业本","笔"],
      "salience":0.7, "valence":0.1, "privacy":"lan", "ttl_ms":1800000 }
```

```
[hub / 记忆服务]
  1. 写入 mem_event（privacy=lan → 永不上云，只在局域网广播）
  2. 因为 confidence=0.82 ≥ 0.8 且 salience=0.7 ≥ 0.6
     → 派生 context 事件
  → publish pet/murasame/context/user.state
    { "state":"busy", "substate":"study", "since":..., "expected_until":...,
      "salience":0.8, "privacy":"lan", "ttl_ms":1800000 }
  3. 因为这是过去 3 天第 4 次「21–23 点写作业」
     → 更新 mem_procedure(kind='habit', key='study.window')，samples=4
```

**四个终端各自反应（并行，互不知晓）**

| 终端 | 订阅 | 动作 |
|---|---|---|
| **桌面桌宠** | `pet/murasame/context/#` | 命中 policy「用户在忙」→ 生成台词（用 affect + relationship 上下文）：「主人又要用功了呀……本座去廊下待着，不吵你。」→ `act/speech.request`（salience 0.4，不打断，用非抢焦点的气泡而非语音） |
| **机器人头** | `sense/phone/visual.activity` + `affect/#` | 表情参数切「安静·专注」：眨眼频率 ↓40%、头部转速 ↓、视线朝屏幕方向 → 用 `act/expression.set` 上报执行结果 |
| **机械臂** | `context/user.state` → 触发本地 policy | 收到 `busy` → 撤销当前排队中的「递水」「整理桌面」等打扰类任务；执行 `ctrl/arm.suppress { "until":"ttl", "reason":"user.study" }`；保留「静默收纳」类任务（低噪音） |
| **智能家居** | `context/user.state` | 客厅灯 → 暖光 4000K、亮度 60%、关闭主灯闪烁；书桌灯 → 亮度升到 80%；音箱音量降到 15%。发 `env/home/light.set`，等 ack |

**结束（30 分钟后 ttl 到期，或手机再次识别到 activity≠study）**

```
[sense] visual.activity { "activity":"idle", "salience":0.4, "ttl_ms":300000 }
[context] user.state { "state":"free", "salience":0.5 }
  → 机械臂自动解除 suppress（ctrl 事件的 ttl 到期）
  → 智能家居恢复原光照场景
  → 桌宠：若 affect.boredom > 阈值，主动说一句（这才是"主动问候"的正确触发点）
  → 记忆服务：把这次「写作业 30 分钟」作为一条 L1 事件落盘，
     如果 salience 累计触发阈值，写进当日日记
```

**为什么这个设计能成立**：四个终端**互不调用**，只依赖 topic 契约。加一个「智能音箱」只要订阅 `context/#`；改桌宠台词不影响机械臂；手机端只要保证 `sense/phone/visual.activity` 的 schema 不变。这正是 Home Assistant 事件总线式的松耦合（[HA 事件系统](https://mintlify.wiki/home-assistant/core/architecture/event-system)）。

**降级策略（必须设计）**：
- hub 不可用 → 桌宠本地仍能响应键盘/鼠标事件；机器人头只做本地表情循环。
- 手机不在局域网 → 走云中继，但 `privacy=lan` 的事件**被丢弃**（不降级、不绕过），只同步 `privacy=sync` 的部分。宁可功能缺失也不破坏隐私承诺。

## 7. 风险与反模式

### 7.1 记忆污染（Memory Poisoning）

**表现**：一条错误记忆被写入后，每次检索都强化它，最终模型把这个错误当事实反复陈述，并据此生成新记忆 → 自我强化闭环。对抗性记忆注入在长程记忆增强的 LLM 上已有专门研究（[ER-MIA, arXiv:2602.15344](https://ar5iv.labs.arxiv.org/html/2602.15344)，**未逐字核验**）。

**缓解**：
1. **两阶段写入**：LLM 抽取的东西先进 `candidate` 区（`mem_profile_buffer` / `mem_fact(status='disputed')`），**不参与检索**。只有满足「≥2 次独立证据」或「用户显式确认」才转 `active`。
2. **强制来源**：`source_event_ids` 为空 → 拒绝写入（DB 层 `NOT NULL` + 应用层校验）。
3. **可撤销窗口**：新记忆 24 小时内可一键撤销，UI 上给「记忆变更日志」。
4. **异常检测**：单日新增事实 > 50 条 → 告警（多半是反思任务跑飞了）。
5. **不要允许 LLM 直接写 `mem_procedure`**（习惯/风格/策略），只允许写候选，`locked=0` 且 `samples ≥ N` 才生效。

### 7.2 幻觉写进长期记忆

**表现**：用户说「我下个月要去日本」，LLM 推理出「用户在日本有朋友」，把后者也写进画像。

**缓解**：
1. **区分「用户说的」与「角色推断的」**：`mem_fact` 加 `claim_type: 'stated' | 'inferred'`。`inferred` 的默认 `confidence ≤ 0.5`，不直插 prompt，只参与检索。
2. **禁止推断写 `profile`**：画像槽位只接受 `stated` 类型。
3. **写入 prompt 与对话 prompt 分离**：抽取任务用「只提取用户明确陈述的事实，不推断」的专用 prompt，且**不给它人格设定**（否则角色会"创作"）。
4. **定期人工抽查**：每周 15 分钟看 20 条新记忆。这是学生项目里最有效的质量手段，别跳过。

### 7.3 隐私泄漏

**表现**：摄像头帧、声纹、位置被上传；日志里打印了完整记忆内容；云服务端明文存储。

**缓解**：
1. `privacy` 白名单闸门（§3.6），default deny。
2. **感知在端侧完成**：手机只发「activity=study」，不发图像。机器人头的人脸识别结果只保留 label，不保留帧。
3. 日志脱敏：记忆内容只打印 `event_id` + `type` + 长度，不打印 `payload`。
4. 服务端零知识加密；备份文件同样加密。
5. 提供「记忆审计日志」（哪条记忆出过设备、去哪了）。
6. 合规：一旦对外 → 敏感信息单独同意（PIPL 第 29 条）+ PIA（第 55 条）+ 删除路径（第 47 条）。

### 7.4 记忆爆炸与检索退化

**表现**：一年后 `mem_event` 十万条，检索 top-k 里混进大量无关记忆，模型被噪声带偏；向量索引膨胀，手机端检索变慢。

**缓解**：
1. **容量预算**：为每层设硬上限。建议 L1 热层 ≤ 5000 条，L2 事实 ≤ 1000 条，L7 反思 ≤ 500 条。超限触发**压缩任务**（把 N 条相似事件合并成 1 条摘要 + 保留原始 id 列表）。
2. **写入前去重**：与最近 200 条做相似度检查，cos > 0.92 → 合并（更新 `rev`、累加 `salience`）而非新增。
3. **分层保留**：热 30 天 / 温 365 天 / 冷归档。归档的不是删除，是移出默认检索域。
4. **检索质量回归测试**：维护一个 50 条的固定问答集（「主人喜欢吃什么」→「辣」）。每次改动检索逻辑后跑一遍，看 top-3 命中率。**这是防止"改着改着就烂了"的唯一有效手段。**
5. **BM25 加 IDF**（§4.2），否则高频词会主导。

### 7.5 多设备人格漂移

**表现**：手机上桌宠说话更冷淡，桌面上更黏人；两端的"人格"越走越远，用户感觉像两个人。

**根因**：人格设定被当作记忆同步了，或者两端各自跑「人格演化」任务。

**缓解**：
1. **人格是契约，不是状态**：`prompt.txt` / `longtext_prompt.txt` / `persona_chunks` **永不参与记忆同步**，三端各存一份完全相同的副本。
   ⚠ **不做 sha256 硬门禁**（全仓目前也没有任何 sha256 校验；`pet.json` 还会被 `pcl_launcher/pet_wizard.py`、`portrait_studio.py` 正常改写）：
   一致性检查失败时**告警 + 回退到备份副本**（`pets/<id>/*.bak-<date>`），**绝不因此拒绝启动**——
   既有启动设计就是"宽容降级"（`pets/pet_registry.py:79-112`：读失败**绝不动盘**、内存兜底返回上次成功清单）。
2. **人格版本化**：`persona_ver` 字段随每次人工修改递增；记忆里记录「这条记忆是在哪个人格版本下产生的」，方便回溯。
3. **LLM 不得改写人格核心**：`mem_procedure(kind='style', locked=1)` 的行只能人工改；LLM 只能写 `candidates`。
4. **漂移检测**：定期（每周）从两端各采样 50 条同 prompt 回复，计算人格向量（用 embedding 均值）的余弦相似度，< 0.85 → 告警。
5. **情绪可以不同，人格不可以**：affect 层允许设备间 ±5% 差异（"手机上的她今天心情不太好"是可以接受的），style/policy 必须完全一致。

### 7.6 其它值得警惕的反模式

| 反模式 | 为什么错 | 替代 |
|---|---|---|
| 把整段对话存进长期记忆 | 检索噪声爆炸，成本线性上升 | 只存事件 + 定期压缩 |
| 用 `history.json` 当主存储 | 全量读写、并发写冲突、无法索引 | append-only 事件 + SQLite |
| 三端各自实现一套记忆逻辑 | 必然漂移，修 bug 要改三遍 | 共享 `schema.sql` + 共享检索权重配置 |
| 让 LLM 决定 `privacy` | LLM 会误判、会"好心"上传 | 写入时按 `type` 查规则表 |
| 向量同步到云端 | 泄漏语义 + 维度不一致 | 只同步文本，端侧重算 |
| 用 CRDT 解决一切 | 你的数据不是协同文档，收益为负 | LWW-per-field + append-only |
| 一次做完 (a)(b)(c) | 学生项目最常见的死法 | 每阶段独立可用、独立有价值 |
| 无验收标准就开工 | 永远"快好了" | 每阶段 5–6 条可测的验收项 |
