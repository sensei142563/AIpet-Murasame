# AIpet 总体规划

> **一句话目标**：让「她」从屏幕里的一个窗口，变成**有记忆、有身体、能陪着你过日子**的存在。
>
> **本规划只谈方法，不谈时间。** 没有排期、没有工期、没有"第几个月做完"。
> 理由：这是个以年计的长期项目，唯一的失败模式是停摆。定死时间只会制造挫败感；
> 定死**方法**（怎么判断一件事做完了、做对了、该不该做）才能让它一直走下去。
>
> 你的原话（8 条设想）全文保留在 [`09-原始设想.md`](09-原始设想.md)，逐条对应见该文件的对照表。

#### D18 的准确表述（不要误解成"没事了"）

> 你说"就当安卓算"——**做法上按安卓走是对的**（`chatter` 继续是 Android 应用，不写 ArkTS）。
> 但底下的事实没变：**nova 12/13 在原生鸿蒙 Beta 名单里，装了原生鸿蒙就不跑 APK。**
>
> 所以处置从"**紧急**"降为"**待办**"：
> - 不急着买测试机了；
> - 但**建议保持系统更新关闭**（零成本，把风险摁住）；
> - 真到那一天，你有两条路：写 ArkTS 版（你说你会），或买/借一台 Android 机。
> - **架构上要为此留门**：不要把 Android 特有 API 渗进 Core 层（`03` ADR-008 的纪律正好覆盖这点）。

### §0.7 ⚠ D25 引出的**新合规约束**：Live2D SDK 有独立授权合同

> **这条很重要，而且和 PIPL 无关——它是 Live2D 公司自己的软件许可。**

**已核实的事实**（[Live2D 官方帮助](https://help.live2d.com/zh-CHS/sdk/sdk_001/)）：

- 公开发布"使用 Live2D Cubism SDK 制作的作品"时，原则上需要签订 **SDK 发行许可证（出版许可协议）**。
- **不需要签合同的情况**包括：
  - 发布的内容**不是用 SDK 做的**（例如从 Cubism Editor 导出的视频）；
  - **仍处于 SDK 试用和开发阶段**；
  - **年销售额低于 1000 万日元的"小型企业"或"普通用户"** 公开作品。
- **但有一条例外**：
  > 「具有**虚拟化身等可扩展性功能**的作品（**可扩展性 APP**）**无需签订 SDK 发行许可证，
  > 但是包括"普通用户"、"小型企业"、"大型企业"在内的所有规模的用户，
  > 每发布一个可扩展性 APP 作品都需要单独签订一个合约。**」

**这对我们意味着什么**：

| 场景 | 是否需要合同 |
| --- | --- |
| 自己编译、自己手机装、不对外发布 | **不需要**（属于"试用和开发阶段"） |
| 把 APK 发给同学装 | 灰色地带 → **按"公开"对待更安全** |
| 开源仓库里**含 SDK 二进制/示例** | 需遵守 SDK 许可协议（下载 SDK 时已同意） |
| 公开发布 App（应用商店/网盘/发布页） | ⚠ **需要**，且因为我们做的是"虚拟化身 + 可扩展功能"（Live2D + 插件/换皮/AR），很可能落在"**可扩展性 APP**"一类 → **每个作品单独签一个合约** |

**做法（写进 `08-风险与合规.md`）**：
1. **现阶段：本地自用**，属于"试用和开发阶段"，不用签；
2. **不要公开分发含 SDK 的 APK**——除非先去 Live2D 官网确认并签好合同
   （[SDK 发行许可证与可扩展性 APP 说明](https://www.live2d.com/zh-CHS/download/cubism-sdk/release-license/)）；
3. **开源仓库里不要提交 SDK 二进制**，写清"请自行从官网下载 SDK 并同意其许可"；
   > ⚠ **现实与例外（2026-10-04 实测）**：本仓库**当前确实跟踪了** `Live2d/Live2DCubismCore.dll`（249,800 字节，首个提交 `4214f5d`），并且**已推送到公开仓库**。用户已决定**接受公开现状、不删除、不改写历史**（见 `08` §1.4.1 与 D26 的口径更正）。此条规则**仍然有效**——只是现状与它不符，别再新增；将来若重新发行，应移出该二进制。
4. **有学生优惠**（[学生优惠说明](https://help.live2d.com/zh-CHS/student/student_01/)）——将来真要发布，先去问；
5. 这一条**不影响现在动手**，但**影响"什么时候能给别人装"**。

> **一句话**：PIPL 第 72 条让我们"自用几乎无合规压力"，
> 但 **Live2D 的 SDK 许可不受 PIPL 影响**——它是软件许可，自用不发布就没事，发布就要签。

#### ⚠ D16 引出的新增风险（**必须现在处理**）

> **事实**：`nova 12/13` 系列已在 **HarmonyOS NEXT（原生鸿蒙）花粉 Beta 招募**名单内
> （[PConline 报道](https://news.pconline.com.cn/1872/18722882.html)）。
> 原生鸿蒙**不运行 Android APK**；有用户反馈需借助 **卓易通** 之类的兼容层才能装 APK
> （[华为开发者问答](https://developer.huawei.com/consumer/cn/forum/topic/0203224422054114010)），
> 而这不是稳定保证（[另一则反馈](https://developer.huawei.com/consumer/cn/forum/topic/0202202686633827516)）。

**这意味着**：`chatter`（Kotlin/Compose，Android）**可能在某天突然装不上你的手机**。

**处理方法（三条，按推荐度）**：

| # | 做法 | 说明 |
| --- | --- | --- |
| **1** ⭐ | **再买一台便宜的二手 Android 手机当专用测试机** | 彻底解耦：主力机随便升级，开发机固定在 Android 上。二手千元内足够跑 `chatter`。**这是最省心的做法** |
| 2 | **主力机不升级原生鸿蒙**（关掉自动更新） | 零成本，但只能拖，不能解决；且哪天系统强制更新就失效 |

## 1. 六条设计原则

### P1. 灵魂唯一，身体多份
只能有**一份**人格、**一份**记忆、**一份**情绪状态。平台再多，也只是"身体"不同。
> 反面教材就是现在：桌面 / `chatter` / `live2D` 三套记忆。再加手机分身、可携带体、家里那台就会变成六套。

### P2. 数据与逻辑分离，能力默认关
动作、表情、触摸区域、硬件映射全部是**数据文件**；引擎里不许出现某个角色或某块板子的专有字符串。
新能力对没配置的用户/角色**默认不生效**。
> 桌面线（A）已经做得很好（`pets/<id>/` + `plugins/` + 能力探测），**继续沿用并推广到 `chatter`**。

### P3. 先仿真后实体，先单点后整体
买零件之前先在软件里跑通控制接口与数据流；真上硬件时，也从 1 路舵机 / 1 个传感器验证起。
> 结合 D7：**硬件之前，仿真先行**。这不只是省钱，而是让"软件侧"在没硬件的三年里照样能长。

### P4. 隐私默认不出门，感知默认可关
摄像头/麦克风/定位数据默认本地、默认不留原始数据、默认可一键关断。
> **可携带体让这条从"技术选择"变成"物理现实"**：一个装着摄像头和麦克风的东西天天跟着你，
> 它会拍到别人、录到别人的话。见 §4 方向 3 与 [`08-风险与合规.md`](08-风险与合规.md)。

### P5. 参考，但不被影响
同学的 `live2D` 是**参考实现**，不是基线、不是依赖、不是"以后合并进来"。
> 正确姿势：**读它的设计文档 → 理解它为什么这么做 → 在 `chatter` 里用自己的方式重写一遍**。
> 禁止：直接拷贝代码/资源、把 `live2D` 作为 git 子模块、让"等同学那边做完"成为阻塞。

### P6. 每周能推进，就不算失败
项目周期以年计，唯一真正的失败模式是**停摆**。
所以任何一件事都要能拆出"**一次坐下就能做完并看到结果**"的最小单元——方法见 [`02-方法库.md`](02-方法库.md)。

```
                              ▲ 事件 Event                ▼ 表达意图 Intent
        ┌─────────────────────┴───────────────┐   ┌──────────────────────────┐
        │            事件总线 EventBus         │   │   意图分发 Intent Router │
        │  桌面：键鼠/屏幕/摄像头/系统状态       │   │  语音→TTS  脸→Live2D/VRM │
        │  手机：相机/传感器/位置/通知           │   │  动作→动画 硬件→MQTT/串口 │
        │  实体：摄像头/麦克风/定位/按键         │   └──────────────────────────┘
        │  通道：QQ/微信/语音/本机 UI            │
        └──────────────────────────────────────┘
                              ▲ 消息                        ▼ 消息
        ┌──────────────────────────────────────────────────────────────────┐
        │                        身体层 Body（每个形态一份）                 │
        │  桌面 Live2D │ 手机 Live2D │ 手机 AR(VRM) │ 可携带体 │ 家居 │ 机械臂 │
        │                                  （家里那台头：以后买成品，先留接口） │
        └──────────────────────────────────────────────────────────────────┘
                              ▲ 协议                        ▼ 协议
        ┌──────────────────────────────────────────────────────────────────┐
        │                     通道层 Channel（每个形态一份）                 │
        │  NapCat(QQ) │ iLink(微信) │ HTTP/SSE │ MQTT │ 蓝牙/BLE │ 串口/ROS2 │
        └──────────────────────────────────────────────────────────────────┘
```

**关键点**：加一个新设备（比如一盏灯、一个可携带体），只需要
① 在事件总线注册它抛的事件、② 实现一个把"表达意图"翻译成该设备指令的 adapter。
**不需要**碰人格、记忆、对话逻辑。

详见 [`03-架构决议.md`](03-架构决议.md) ADR-000 / ADR-008。

### 2.1 双轨模型（D4）

| 形态 | 用什么 | 用在哪 | 动作怎么驱动 |
| --- | --- | --- | --- |
| **日常形态** | **Live2D**（`.moc3` + 表情 `exp3.json`） | 桌面、手机竖屏 | 语义动作名 → Live2D 参数（现有做法） |
| **实体/空间形态** | **VRM（3D）** | 手机 AR、未来的实体设备、家里那台头 | 语义动作名 → VRM Humanoid 骨骼动画 |

**两边共用一份动作档案**：档案里用**语义键**（`点头`/`挥手`/`扭腰`）描述动作，
再由各形态的 adapter 翻译成自己的参数或骨骼。这正是 ADR-004 的价值——
**加一个动作只改数据，不改代码，且两种形态同时获得这个动作**。

### 2.2 记忆的分层（与桌面线已有模块对应）

| 层 | 内容 | 桌面线已有对应 | 跨端策略 |
| --- | --- | --- | --- |
| 工作记忆 | 当前对话上下文 | 对话历史 | 各端本地，**不同步** |
| 情节记忆 | "什么时候发生了什么"（含日记） | `history.json`、`long_history.json`、日记 | **只追加**（天然无冲突） |

### 2.3 算力与音频的分工（D21 的直接结论）

> 你问："声音的变化能不能由手机所控制改变？" —— **能，而且这正是最省事的架构。**

```
   手机 / 电脑（大脑）                          核（哑巴音箱）
   ├─ LLM 生成台词                    ──┐
   ├─ LLM 决定情绪/语气                 │
   ├─ TTS 合成音频（音色/语速/情绪都在这里）│  音频流
   ├─ 音量、音效、变声、混响             ├──────→  核只做三件事：
   └─ 一切可调参数                      ──┘          ① 收音频流，播出来
                                                     ② 上传麦克风音频
                                                     ③ 上报电量/在线状态
```

**结论**：
- **音色、语速、情绪、音量、变声……全部在手机/电脑侧决定**，核**不需要任何音频处理能力**；
- 核越简单 → 越省电、越便宜、越不容易坏；
- 换皮、换核、换手机，**声音风格跟着"她"的设置走**，不跟着硬件走；
- 唯一要注意的是**延迟**：音频流要低延迟（这是"哑终端"方案的唯一技术门槛）。

**这条同时也回答了 Q17-c**：换皮**不改**声音——声音属于"她"（软件侧设置），
皮只提供外形。如果想让某个皮有专属音色，那也应该是"**设置项的预设**"，而不是写死在皮里。

### 2.4 App 是"她"的主界面，微信只是通道之一（D23/D24）

> 你说"软件名字啥的都要变，以及一系列杂七杂八的功能都要在它上面扩充"。
> 这是**定位升级**，不只是改个名字。

**现在**：`chatter` 的自我认知是"微信桌宠"（`app_name` = `AIpet 微信桌宠`），微信是它的全部。
**目标**：它是"**她**"的主界面，微信只是她能联系到你的**一个通道**。

```
                    ┌──────────────────────────────┐
                    │   App = 她（主界面）           │
                    │  见面、说话、看记忆、管设置      │
                    └───────────┬──────────────────┘
        ┌───────────┬───────────┼───────────┬────────────┐
        ▼           ▼           ▼           ▼            ▼
     微信通道    本机直聊     QQ(桌面)    AR 形态     核/皮设备管理
     (ClawBot)  (D23 新增)              (VRM)      (配对/电量/隐私开关)
```

**为什么这条重要（三个具体后果）**：

| 后果 | 说明 |
| --- | --- |
| **① 有一个"永远能用"的入口** | D23 的本机直聊 = **不依赖任何第三方协议**。微信变了、网断了，你还能跟她说话 |
| **② 功能有地方长** | 记忆管理、人设、语音设置、设备配对、AR、日程提醒……**都该长在这个 App 里**，而不是散在各处 |
| **③ 名字和图标要能代表"她"** | 不再是"微信桌宠"；这是一个**陪伴应用**。见 [`07-待定选择支.md`](07-待定选择支.md) Q21 |

**做法（不急着一次做完）**：
1. 先把 **D23 的本机直聊页**做出来（它就是"主界面"的第一块地）；
2. 再逐步把微信相关的字样从界面与元数据里退到"通道设置"里；
3. **改名放到最后**——等主界面成型了再改，避免改了一半的两栖状态。

| 事项 | 达标长什么样 |
| --- | --- |
| **主界面化**（D24） | App 自我认知是"她"而不是"微信桌宠"；微信退到"通道设置"里 |

**解决什么**：从"你打字她才回应"变成"她主动知道发生了什么"。

| --- | --- |
| 事件总线 v1（MQTT 语义 + hub） | 至少 3 类设备订阅同一事件；`ttl_ms` 语义生效 |
| 手机摄像头端侧分类（"在写作业"） | **不上传图像**，只发结构化事件 |
| 物品识别 | "桌上有什么"能正确说出；Top-5 准确率实测 |
| 纯视觉动捕（D5 第一步） | 手机摄像头 → 虚拟形象跟着动 |
| 定位/在场感知（为可携带体铺路） | 知道"你在家/在外面"，不掉电 |

**入口**：L1 的事件模型 + L2 的 AR/渲染。
**纪律**：所有感知**端侧完成**，只发结构化结果，不发原始音视频（P4）。

### L4 · 实体：她可以出门，也可以在家有个身体

**解决什么**：D8/D9/D11/D12——**先有「一个核 + 可换的皮」，再有"家里的成品身体"**。

| 事项 | 达标长什么样 |
| --- | --- |
| **核的软件仿真**（**现在就能做，不需要硬件**） | 用假数据跑通"核 → 事件 → 她回应"全链路 |
| **物理接口标准**（ADR-010） | 核的尺寸/固定/开孔/充电写进契约，**冻结** |
| **躯体身份**（`device_id` 属核，`skin_id` 属皮） | **换皮之后记忆连续**，还是同一个她 |
| 皮的选型（D12） | 按三条判据（能拆开 / 内腔够 / 不用自带电子件）实测，有一份比较表 |
| **功耗预算表** | 能回答"这样能撑多久"（含手机热点那部分耗电） |
| 配对、注销、丢失处置 | 一个新核从零到可用有明确步骤；丢了能远程注销 |
| 隐私软件开关 | 关掉时**硬件真的停止采集**、状态持久化、可审计、默认关 |
| 家里那台头（D9） | **只留接口**：`Expression Intent` 的 `hw` 段 + 一个假驱动 |

**入口**：L3 的事件总线。**硬件本身按 D7 排后，但"买现成的皮/核"现在就可以做。**

### L5 · 现实：她在你眼前

**解决什么**：投影、机械臂、智能家居——**让"她"影响物理世界**。

| 事项 | 达标长什么样 |
| --- | --- |
| 智能家居最小闭环 | 说"好冷"→ 开暖风；她能读温湿度（**这是性价比最高的一项**） |
| 投影形态 | AR 验证完之后再评估；**不早于 AR** |
| 机械臂（**买套件，不自制**） | 通过 `hw` 指令驱动，能挥手/递东西 |
| 动捕驱动机械臂 | 动捕 → IK → 关节角，闭环可复现 |

**入口**：L3 感知 + L4 的 `hw` 接口。**除智能家居外，其余都需要硬件预算，按 D7 排队。**

### 3.7 层间依赖（唯一的顺序约束）

```
L0 地基 ──┬─→ L1 灵魂（记忆协议）──┬─→ L2 手机（记忆互通）
          │                        ├─→ L3 感知（事件总线）
          │                        └─→ L5 家居（同一台家庭服务器）
          └─→ L2 手机（渲染/AR，可完全并行，不等 L1）

L3 感知 ──→ L4 实体（可携带体）
L4 实体 ──→ L5 现实（机械臂/投影）
```

**允许的跳法**：
- 想马上看到效果 → **直接做 L2 的 AR/VRM**（零硬件成本，不依赖任何东西）。
- 想马上让她"有用" → **直接做 L5 的智能家居**（几百块，风险最低）。
- 想打地基 → L0 + L1。

**不允许的跳法**：在没有 L1 记忆协议时做 L4（会造出第四套记忆）；
在没有事件总线时做 L5 的机械臂（会写死一堆一次性代码）。

## 4. 方向规划（对应你的 8 条设想）

- **目标**：一个 App —— 会动、会记事、能接微信、和桌面共记忆。
- **方法**：
  1. **先读后写**：把 `live2D` 的 `设计文档-动作表情系统.md`、`优化方案.md`、`修改记录.md` 读懂，
     写成一份《我理解的 Live2D 集成方案》放在 `chatter/docs/` 里（**只写思路，不拷代码**）；
  2. **自己实现**：在 `chatter` 里用 Kotlin 重写渲染接入与 act 解析，**不引入 `live2D` 的任何文件**；
  3. **动作数据化**：`avatar_profile.json` 进角色包，加动作只改 JSON；
  4. **通道与渲染解耦**：微信通道照旧，"她动"由 `Expression Intent` 驱动，互不耦合；
  5. **记忆绑定**：先做导出/导入（不需要服务），再谈实时同步。
- **做完了长什么样**：微信来消息 → 手机上的她做表情、出声；桌面聊过的内容，手机上问得出来。
- **依赖与红线**：
  - 依赖 L1 的记忆协议（只影响"互通"部分，渲染部分可并行）；
  - **红线**：`chatter` 仓库里不出现 `live2D` 的文件（D2）；不因为"等同学"而阻塞（P5）。

### 方向 3 · 可携带体 = **皮 + 核**（**不是表情头**）

> **这一条我先前理解错了，按 D8 重写。**
> 你要的不是"一张会做表情的脸"，而是**一个能带出门、还能聊天的实体**：
> 身体里装上**摄像头、录音、语音、定位、联网**这些功能块。它**不需要做表情**。
>
> **2026-10-04 晚再修订（D11/D12）**：载体要**可拆卸、可多个**——
> 可以塞进毛绒玩偶，也可以塞进人形娃娃。**所以正确的结构不是"一个实体"，而是「一个核 + 可换的皮」。**

#### 3.1 核心模型：核（Core）+ 皮（Skin）

```
        ┌───────────── 皮 Skin（可替换、可多个）─────────────┐
        │  毛绒玩偶  │  人形娃娃  │  以后自制外壳（D7 之后）   │
        └──────────────────────┬────────────────────────────┘
                               │  统一的"躯体接口"
                    ┌──────────┴──────────┐
                    │   核 Core（一个）     │
                    │  摄像头 / 麦克风      │
                    │  扬声器 / LED 指示    │
                    │  定位 / 联网(手机热点) │
                    │  电池 / 按键 / 电量   │
                    │  身份：device_id      │
                    └─────────────────────┘
```

**为什么必须这样分**：你说"可能是可以拆卸的，亦或者多个"——
一旦载体可换，**核就必须能被取出来装到另一个皮里**。
所以设计约束从"做一个玩偶"变成了"**做一个能被塞进玩偶的模块**"。

#### 3.2 三个直接推论

| 推论 | 说明 |
| --- | --- |
| **① 需要一个物理接口标准** | 核的尺寸、固定方式、开孔位置（摄像头/麦克风/喇叭）、供电方式必须定下来。见 `03` ADR-010 |
| **② 需要一个"躯体身份"概念** | 每个核/皮都是独立设备 → 要有 `device_id`、配对、注册/注销。**换皮之后记忆必须还是同一份**（这正是 L1 记忆协议存在的意义） |
| **③ "买皮"比"做皮"划算得多** | D12：直接复用现成产品（玩偶 / 人形娃娃 / 现成的成人向硅胶产品）。白得外壳、皮肤、内腔、电池位 |

#### 3.2.1 尺寸：**宽松**（D19）

> 你定了参照物：**初音 FUFU 那种约 50cm 的毛绒**（[同类产品参考](https://dengekionline.com/article/202602/65177)）。
> 这比"塞进小挂件"宽松得多，**我原来担心的"塞不进"可以排除**。

| 参照 | 尺度 | 对核的意义 |
| --- | --- | --- |
| 50cm 级毛绒 | 腹部/背部内腔通常有拳头到手掌大的空间 | **核可以做到「一包烟 / 名片盒」级别**，电池与喇叭都有余量 |
| 小挂件（10cm 级） | 内腔极小 | 这是**下界**——核不必做到这么小 |

**建议的核目标尺寸**（待你实测手上的皮来定，这里只给量级）：
- **约 80 × 55 × 20 mm 量级**（比名片盒略小）——放得下摄像头模组、麦克风、小喇叭、电池与按键；
- **判据不是"能不能塞进 50cm 的 FUFU"，而是"能不能塞进你最想带出门的那个皮"**。
  所以要按**最小的那个皮**定，其余都是余量。

> **这直接决定电池**：80×55mm 的面积能放 1000–2000mAh 级电池 → 续航比小挂件宽裕得多。
> 具体数字等 §5.4 的功耗预算表算完再定。

#### 3.2.2 声音：**开孔外露**（D20）

> 你说"我会把麦克风和扬声器的位置漏出来的"——**这条障碍排除了**。
> 我原来担心的"塞进皮里喇叭被闷住、声音变难听"不再成立。

**但仍然要守两条**：
1. **开孔位置要对齐**：皮上的孔位与核上的麦克风/喇叭位必须对得上（写进物理接口标准，ADR-010）；
2. **麦克风不要正对喇叭**（会啸叫/回声）；摄像头孔**不要开在会被挡住的位置**（抱着玩偶时最容易挡）。

**声音本身怎么处理**：见 §2.3——**音色/语速/情绪全在手机侧决定**，核只管播放。

#### 3.3 复用现成载体（D12）的好处与坑

**好处**：外壳、皮肤手感、内部空腔、电池位、甚至充电口**全是现成的**；坏了/看腻了换一个，
成本远低于自制；毛绒玩偶天生适合"带出门"（不怕磕碰、手感好、旁人不会觉得奇怪）。

**坑（买之前必须实测）**

| 坑 | 怎么实测 | 状态 |
| --- | --- | --- |
| **内腔空间不够** | 先看/量：能不能塞进核 | ✅ **已排除（D19）**：50cm 级毛绒的内腔远大于此 |
| **结构封死、不好开** | 看原本是"可拆洗"还是"整体缝合"；缝死的要自己拆，容易毁 | 仍需实测 |
| **自带协议与 App 不透明** | 它自带的蓝牙/App 通信往往是私有的、可能**上传数据**。**我们的核不碰它的电路，只借壳** | 仍需实测 |
| **隐私（成人向品类尤甚）** | 这类产品常自带摄像头/录音——**用它自带的就等于把隐私交给厂商**，所以**只用壳** | 仍需实测 |
| **散热与走音** | ~~喇叭被闷住会变难听~~ | ✅ **已排除（D20）**：麦克风/扬声器在皮上开孔外露 |

> **买皮的三条判据**：① 能拆开（可拆洗/有拉链/背板可开）；② 内腔够放核；③ **能不用它自带的电子件**。

#### 3.4 方法（**现在是软件先行的阶段**）

1. **先定义"核"的抽象接口**，不要先想硬件：
   ```
   核 Core = { 传感器输入: 摄像头 / 麦克风 / 按键 / 定位,
               输出: 扬声器 / LED 指示 / 振动(可选),
               状态: 电量 / 在线 / 所在网络,
               身份: device_id + 配对密钥,
               皮: skin_id(可空) }        ← 换皮不改身份
   ```
   在软件里先做一个**假核（模拟器）**：用手机或电脑模拟它抛事件、收指令；
2. **跑通"核 → 事件 → 她回应"全链路**，此时一行硬件代码都不需要；
3. **算清功耗预算**（`05` §5.3）：**注意 D13——联网走手机热点**，
   所以核里**不需要 4G 模块**，但**手机热点的耗电要算进总账**；
4. **选皮**（D12）：按 §3.3 的三条判据实测，**别盲买**；清单见 [`05-采购与预算.md`](05-采购与预算.md) §5；
5. **配对与隐私**：核/皮怎么绑定、哪些数据永不出设备、**丢了怎么远程注销**（可携带体丢在外面是最坏情况）。

#### 3.5 做完了长什么样

- **软件层**：假核跑通全链路，事件与指令都有 schema；**换皮时记忆连续**（还是同一个她）；
- **硬件层**：有一个能带出门的核，装在一个皮里；你在外面跟它说话，它用**同一份记忆**回应你；
- **可扩展**：换一个新皮，**不需要改软件**。

#### 3.6 关键难点

- **续航与发热**（可穿戴设备的永恒问题；热点模式让核更省电，但手机更热）；
- **核的尺寸**：摄像头 + 麦克风 + 喇叭 + 电池塞进一个小腔体，是真实的机械难题；
- **在外面被拍到的别人**（隐私，见 §3.7）。

#### 3.7 红线（比家用设备严格得多，因为它会跟着你进公共场所）

> **按 D14：隐私要求采纳 D（不录他人 + 有指示 + 不伪装），但开关用软件实现。**

1. **不录制他人**：摄像头只在本地做即时判断，原始帧**不落盘、不上传**；
2. **录音/拍摄要有明显指示**：LED 或提示音，让周围的人知道它在听；
3. **开关用软件实现**（D14），因此**必须做到状态真实**：
   - 关掉时**硬件真的停止采集**（不是"采集了但不发"）；
   - 状态**持久化**（重启后仍是关的）；
   - **可审计**（能查到"什么时候开过"）；
   - **默认关**（采集类功能一律默认关）。
4. **不伪装成真人**：对外要能说明这是 AI（见 [`08-风险与合规.md`](08-风险与合规.md)）。

> **关于"要不要加硬件开关"**：你选了软件开关，我按你的定。但留一句实话——
> 软件开关的失效方式是"**你不知道它在录**"，硬件开关的失效方式是"**多了个零件**"。
> 哪天想加，成本很低（一个拨动开关串在摄像头供电线上）。**留作可选项，不阻塞现在。**

- **依赖**：L3 的事件总线（软件接口）；手搓硬件排在 D7 之后，
  但**买皮/买现成核不受 D7 限制**（那属于"用成品"）。

### 方向 4 · 3D / Live2D 投影

- **现状**：仓库里有 Live2D 模型（`.moc3`）；`场景素材/` 有 4 张背景图。
- **目标**：一个悬浮/半透明的"她"出现在现实空间里。
- **方法**：
  1. **先做手机 AR**（方向 8 的一部分）——它比投影便宜 100 倍、效果更稳，且能复用同一套 VRM 资产；
  2. AR 验证完之后，再评估投影形态（候选：亚克力全息金字塔 / 雾幕 / 旋转 LED）；
  3. **判据**：如果"在手机屏幕里看到她站在房间里"已经够打动你，投影就不必做。
- **做完了长什么样**：AR 里有一个稳定跟踪、不穿帮、会看你、会说话的她。
- **关键难点**：投影的亮度/对比度（很暗）、可视角度窄、环境光干扰、Live2D→3D 的资产转换。
- **依赖**：D4 的双轨决策（VRM 资产）。

### 方向 5 · 家用机器人头 + 微机械臂（**都等成品**）

> **按 D9：不手搓。** 这一条现在的任务只有"留对接口"，不占工期。

- **现状**：零。
- **目标**：家里书桌上有一颗会做表情、会说话的头；有一只能做事的臂。
- **方法**：
  1. **只做接口，不做结构**：`Expression Intent` 的 `hw` 段 + 一个**假驱动**（打印/可视化），
     让"她说话时头会动"这件事在软件上先成立；
  2. **观察市场**：等成品（桌面机器人、开源头的成品套件）降价/成熟，**直接买**；
  3. **买之前先问三件事**：能不能收 MQTT/HTTP 指令？能不能自己换模型/人设？能不能本地跑（不强制上云）？
  4. **不要自制结构件**——那是最大的时间黑洞（ADR-006）。
- **做完了长什么样**：买回来的成品能被她通过 `hw` 指令驱动，表情与语音同步，且用的是她自己的人格和记忆。
- **关键难点**：成品的开放性（很多消费级产品是封闭的，接不进来）；
  买之前必须验证"可编程"这一条，否则买回来是个玩具。
- **依赖**：L3 事件总线 + `hw` 接口。**硬件采购排在 D7 之后。**
- **如果将来真要自制表情头**：调研结论仍然有效——**7 路舵机（2眉+2睑+2嘴角+1下颌）+ 圆屏眼球**，
  不要堆 20 路。存档在 [`04-调研附件.md`](04-调研附件.md) §3.2。

### 方向 6 · 智能家居

- **现状**：零，但这是**性价比最高的一环**：几百块就能让"她"影响物理世界。
- **目标**：她能感知环境（温湿度/门磁/人在不在）并控制设备（灯/插座/风扇）。
- **方法**：
  1. **一台常开的家庭服务器**（旧电脑/N100 小主机）跑 Home Assistant：
     这台机器同时是**记忆服务**（D3）与 **TTS 服务**的宿主，一次投入办三件事；
  2. **先接一个灯 + 一个温湿度传感器**，跑通"她 → MQTT → 灯亮"；
  3. **ESP32-C6 自制节点走 ESPHome + MQTT**（成熟稳定），**不要一上来啃 Matter 原生固件**；
  4. **HA 是唯一真相源**：桌宠不缓存设备状态，只发意图，由 HA 执行。
- **做完了长什么样**：说"好冷"→ 暖风开；她读得到温湿度；断网也能亮灯（自动化跑在本地）。
- **关键难点**：协议碎片化（米家/涂鸦/Aqara 各有脾气）、内网配置、**安全**（别把家里开关暴露到公网）。
- **依赖**：ADR-001 的"家庭服务器"就是这台机器。

### 方向 7 · 说话不像人 + 跨模块记忆

> **按 D6：语音部分暂时搁置。** 记忆部分按 L1 推进。

- **现状**：TTS 音质可以，但"一听就是 AI"；三个代码库三套记忆互不相通。
- **目标**：她说话像人；她的记忆只有一份。
- **方法**：
  - **记忆**：按 L1 走（协议 → SQLite → 检索加权 → 回归集 → 静默记忆服务）。
  - **语音（搁置中，保留方法不排期）**：如果哪天重新启动，**顺序不能变**——
    先做**零成本**的三件事（口语化改写 / 标点韵律规则表 / 副语言拼贴），
    用盲听 A/B 验证有没有效，**再**考虑换 TTS 模型。
    调研结论仍然是：**55–65% 的"AI 味"在文本层和轮次层，不在声学模型。**
    完整方法存档在 [`04-调研附件.md`](04-调研附件.md) 第一章。
- **为什么搁置**：换 TTS 涉及显存、延迟、链路稳定，**很容易把整个项目拖崩**，
  而收益在文本层没做完之前并不明显。
- **依赖**：无（记忆部分可以马上做）。

### 方向 8 · 摄像头 + 云/主机验算 + 微电波 + AR 叠加 + 交互

这是你设想里**最前沿、也最容易做错**的一条。先给三条硬结论（依据 [`04-调研附件.md`](04-调研附件.md) §2）：

> 1. **「厘米级 + 无标记 + 低成本 + 实时」四元组目前不存在**，必须放弃其中一项。
>    个人项目现实的最优解是放弃"毫米级"，接受 **1–10 cm 级**精度。
> 2. **你设想里的"外置微电波发送接收"不是动捕。** 它的真实身份是 UWB / BLE AoA / Wi-Fi RTT / 毫米波雷达，
>    能做**分米级的"人在哪"**，**做不到关节角度级别的姿态**。
>    它的正确角色是「粗定位 + 跟随 + 防丢 + 存在感知」——**不要指望它做精准动捕**。
> 3. **最该先做的是手机 AR**：零硬件成本、体验冲击最大。

逐层拆解：

| 子问题 | 现实可行性 | 方法 |
| --- | --- | --- |
| 手机摄像头做姿态/手势识别 | **完全可行**，手机上就能实时跑（MediaPipe Pose 单目即可） | **先做这个** |
| "电脑/云主机验算" | 可行，但要算清延迟预算 | **端侧做 SLAM/渲染/动捕融合，云侧只做重模型推理**；端到端压 100–200ms |
| "外置微电波"（UWB/BLE AoA/Wi-Fi RTT/毫米波） | **部分可行**：UWB 分米级、BLE AoA 1–2m、毫米波能做存在/呼吸感知 | **不能替代动捕**；最有价值的用法是**融合定位以抑制漂移**，以及给可携带体做"在不在家"的判定 |
| 精准动捕（D5） | 纯视觉有天花板（单目 10–20° 关节角误差） | **MediaPipe（0 元）起步** → 需要精度再上 SlimeVR（自建 ¥570–800）→ 再不够才谈光学 |
| 物品识别 | 可行（**YOLO26** 已核实存在，NMS-free；**SAM 3** 已核实存在） | 先做"认得桌上的东西"；**注意 Ultralytics 是 AGPL-3.0，商用要开源或买 license** |
| **AR 叠加二次元 3D** | **成熟可行**（ARCore/ARKit + VRM；或 three.js + `@pixiv/three-vrm` + WebXR） | **★ 这条应当最先做**，投入产出比最高 |
| 自主做动作 + 交互 | 可行（行为树/状态机 + 意图系统） | 复用 ADR-004 的动作档案 |

**国内特有的两个坑**：① ARCore 的 **Geospatial API 依赖 Google 街景，大陆基本不可用**（只能走纯本地 SLAM）；
② **微信内置浏览器不支持 WebXR**（需 Chrome/三星浏览器 + HTTPS）。

**第一个里程碑（不含时间）**：
> 手机 AR 里放一个 VRM 模型，让它站在你房间地板上，会看你、会点头、会用 TTS 说话。
> **不需要买任何硬件**，就能验证"她在现实里"这件事的核心体验。

- **关键难点**：光照与尺度估计、跟踪漂移、手机发热降频、云端往返延迟、
  多传感器**时间同步与坐标系统一**（最大的隐形成本）。
- **依赖**：D4 的 VRM 资产、L3 的感知。

## 5. 验收：怎么知道"变好了"

> 从"感觉在变好"变成"**证明**在变好"的唯一办法是留数字。
> 详细方法（怎么测、样本量、显著性）见 [`02-方法库.md`](02-方法库.md)。

| 维度 | 指标 | 现在 | 目标 |
| --- | --- | --- | --- |
| 稳定 | 桌面连续运行 72h 不崩 | 未测 | 通过 |

## 6. 协作分工

**你（CS，山大）**：AI 层、记忆与协议、桌面引擎、手机端、云侧服务、工程化与测试、文档与决策。
**同学（电子信息，杭电）余\***：电路设计、PCB、传感器选型与驱动、电源与安全、结构与硅胶工艺、单片机固件。**本项目协作者：申余不是鱼**（软件侧协作）。
**同学张\*泽的项目 `live2D`**（他同时是 `chatter` 的协作者）：只读参考（D1/D2/P5），贡献是"思路"、不是"代码"；我们只按用户要求**清过它源码里两处硬编码 key**（`docs/handover/2026-09-24.md` §30.1），**不改变它"别人的项目"的定性**。

**接口（唯一的接口文件）**：ADR-000 的 `hw` 段 JSON。
```
你产出：{"target":"arm","cmd":"wave","params":{"speed":0.5}}
他实现：收到 → 舵机序列 → 动作完成 → 回报 {"target":"arm","event":"done"}
```

**协作纪律（沿用桌面线的 handover 规范）**：
1. 一次交接一篇 `docs/handover/YYYY-MM-DD.md`；
2. **改动接口先改文档再改代码**；
3. 各自模块各自的可运行 Demo，不许"我这边跑不起来是因为他那边没做"；
4. **硬件侧也要有仿真模式**——没有实物时，一根 USB 线或一个假驱动就能跑通逻辑。
   这条对你们两人都是救命的，而且**在 D7 的这三年里，它是硬件侧唯一能推进的方式**。

**因为你这边先开工，所以现在的分工实际上是**：
你负责**全部软件 + 全部接口定义 + 全部仿真**；同学的硬件工作排在他方便的时候。
**不要让"等硬件"成为你停下来的理由**——接口和仿真足够你走很久。

## 7. 止损线（什么时候该停）

| 分支 | 停止条件 | 停下来的做法 |
| --- | --- | --- |
| 手机端 Live2D 集成 | 自己重写渲染连续受阻，且看不到收敛 | 退一步：`chatter` 只做"文字 + 立绘 + 表情包"，Live2D 留给桌面 |
| 记忆服务 | 冲突问题反复出现 3 次修不好 | 退回"单机主库 + 手动导出导入"（静默模式正好是这个退路） |
| AR/VRM | 试了两种模型格式仍跑不动 | 先只做"2D 立绘 + 视差"的轻量 AR |
| 可携带体 | 功耗预算算下来撑不过 2 小时 | 降级为"外出时用手机当身体，实体只放家里" |
| 语音拟人化 | 一旦重启后指标不涨、或链路频繁崩 | **回到搁置状态**（本来就是搁置的） |
| 投影 | 试了两种方案仍看不清 | 放弃，手机 AR 已经够 |
| 绩点 | 学期绩点显著下滑 | 项目只保留 L0 维护 + 一个想做的点 |

> 写下来不是咒自己失败，而是**给自己一个体面的退出口**——
> 没有退出口的项目，最后往往是被"不敢承认做不完"拖死的。
