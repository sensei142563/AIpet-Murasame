# 方法库

> 这份文档不含任何时间规划。它回答的是：**遇到一件事，怎么做才对。**
>
> 为什么要单独写这一份：这个项目的周期以年计，**方法比进度重要**。
> 定死时间只会制造挫败感；定死方法才能让它一直走下去。
> 用法：开工前扫一眼 §2 里对应的方法；卡住时翻 §5；做完一件事用 §3 自检。

---

## 1. 做任何一件事的六步

不论大小——加一个动作、接一个设备、做一个页面——都走这六步。
**其中第 1、6 步最常被跳过，而它们恰恰是最省钱的两步。**

| 步 | 做什么 | 产出（必须落在文件/截图里） |
| --- | --- | --- |
| **1. 量基线** | 动手前先测现状：跑多快、占多少内存、现在是几秒、现在是几成准确率 | 一个数字，写进 `01-现状盘点.md` |
| **2. 定判据** | 写下"怎么算做完了、怎么算做对了"。写不出判据 = 还没想清楚 | 一句可测的话（含数字） |
| **3. 造最假的版本** | 用假数据/纸板/写死的常量先让它"跑起来" | 一个能演示的东西，哪怕丑 |
| **4. 真数据替换** | 把假的部分逐块换成真的，一次换一块 | 每换一块都能运行 |
| **5. 自证** | 用第 2 步的判据验一遍，留下证据 | 截图 / 数据表 / 录屏 / 单测输出 |
| **6. 写下来** | 更新盘点、写清"没做什么、为什么" | 文档改动 + 一次本地提交 |

> **第 3 步是这套方法的核心。** 先让它跑起来（哪怕全是假的），
> 你才有东西可以改；一直想"等设计完美了再写"，是长期项目最常见的死法。

## 2. 十二条核心方法

### M1. 先仿真后实体
**做法**：接口定义好了，就先写一个"假实现"（打印日志、画个方块、发一条假事件），
让整条链路先跑通。真硬件以后接进来，只换那一个 adapter。
**为什么**：① 省钱；② **在硬件到手之前，软件侧照样能长**（这条在 D7 的三年里是唯一活路）；
③ 出问题时能立刻判断"是逻辑问题还是硬件问题"。

### M2. 先量再改
**做法**：任何"优化"之前，先写下当前数字。改完再测一次，数字不涨就回滚。
**为什么**：没有基线，"优化"就是心理安慰。而且基线本身极便宜——
一行计时、一个内存快照就够了。

### M3. 一次只改一件事
**做法**：一次提交只做一件事；不夹带无关重构（沿用桌面线的工程原则）。
**为什么**：出问题时能一眼看出是哪次改坏的。三线合并、加硬件这种大动作，尤其要这样。

### M4. 用数据代替感觉
**做法**："感觉好点了"不算结论。要么留数字（延迟、准确率、体积），要么留对照（A/B）。
**反例（一定要避免）**：改了语音，自己听了一遍觉得"自然多了"，就宣布成功。
**正例**：20 句固定台词 × 旧新两版 × 随机顺序 × 10–15 位听者，记偏好率，做符号检验。

### M5. 盲听 / 盲测 / 双盲
**做法（做主观评价时）**：
1. 固定测试集（例如 20 句台词），**提前写好**，不许改题；
2. 每项生成两个版本，**随机顺序**播放；
3. 找足够多的人（见 §3.3 的样本量）；
4. 至少有一项对照是"已知正确答案"（例如混入一段真人录音）；
5. 记录原始数据（谁、哪一轮、选了什么），不只记结论。
**为什么**：主观项目最容易自欺。**你自己的耳朵不算证据。**

### M6. 端侧优先，只发结论
**做法**：感知类的东西（图像、音频、位置）**在设备上处理完**，只把结构化结果发出去。
例如：不发图像，只发 `{"activity":"study","confidence":0.82}`。
**为什么**：① 省带宽与延迟；② 隐私（原始数据不出设备）；③ 云端算力更便宜。

### M7. 接口先行
**做法**：改接口**先改文档**，再改代码；文档里写清字段、单位、取值范围、失败时怎么办。
**为什么**：你和一个外地同学协作，接口是唯一的合同。
**具体格式**：见 [`03-架构决议.md`](03-架构决议.md) ADR-000 的 `Expression Intent` 与 `hw` 段。

### M8. 状态用"会过期的断言"，不要用"显式取消"
**做法**：发"30 分钟后自动失效的 `在写作业=true`"，而不是发"在写作业=true"、之后再发"不写作业了"。
**为什么**：**缺失即失效**，消掉一大类状态同步 bug（对方掉线、崩溃、忘记发取消）。
对应字段：事件的 `ttl_ms`。

### M9. 只读参考，自己重写（针对 `live2D`）
**做法**：
1. 读 `live2D` 的**设计文档**（`设计文档-动作表情系统.md`、`优化方案.md`、`修改记录.md`）；
2. 写下《我理解的 XX 方案》——用你自己的话，讲清它**为什么**这么做；
3. 在 `chatter` 里**用自己的代码**重写一遍；
4. **在文档里说明思路来源即可**（例如写进自己的笔记/设计文档：思路参考自同学项目的设计文档）；**提交信息保持简洁、不写他人署名**，**不拷贝文件**。
**禁止**：把 `live2D` 的代码/资源/`.moc3`/大文件搬进主仓库；把它作为子模块；
让"等同学那边做完"成为你停下来的理由。
**为什么**：那是同学的项目（D1/D2）。**借鉴思路是学习，拷贝文件是负债**——
你会背上一份你不敢改、也改不懂的代码。

### M10. 参考纪律（自查清单）
每次提交前问：
- [ ] 这个提交里有没有 `live2D` 的文件？（**必须没有**）
- [ ] 这段代码我能不能解释每一行为什么这么写？
- [ ] 如果同学明天大改他的项目，我这边会不会坏？（**不该坏**）

### M11. 测基线 + 回归集
**做法**：为每个"容易改坏"的东西建一个**固定的小测试集**（记忆检索 50 条问答、
act 解析 20 个边界用例、界面渲染 7 张截图）。改完就跑一遍。
**为什么**：这是防止"改着改着就烂了"的唯一有效手段，也是唯一能给你安全感的机制。
**成本**：很低。50 条问答手写一个下午，能保你半年。

### M12. 仿真模式是硬件侧的长期活法
**做法**：任何硬件都要有一个"不用实物也能跑"的模式（假驱动 / 回放日志 / 手动触发）。
**为什么**：结合 D7（三年内不做硬件），这意味着**你现在就能把硬件相关的软件全写完**。
等哪天真买了设备，插上就能用。

## 3. 验收方法（怎么证明"变好了"）

### 3.1 三类证据，按可信度排序

| 等级 | 证据形式 | 例子 |
| --- | --- | --- |
| **强** | 可复现的数据 / 对照实验 | 50 条回归集 top-3 命中率 82%；盲听偏好率 68%、p=0.03 |
| **中** | 截图 / 录屏 / 日志 | "微信来消息，她做了表情并出声"的录屏 |
| **弱** | 口述 / 记忆 | "我试了一下，好像可以" |

**规则**：**弱证据不算验收。** 说"应该没问题"的一律视为未完成
（沿用桌面线 `docs/handover/README.md` 的既有原则）。

### 3.2 客观指标清单（可直接用）

| 维度 | 指标 | 怎么测 |
| --- | --- | --- |
| 速度 | 首字延迟 | 打时间戳：发请求 → 收到第一个字 |
| 速度 | TTS 首包延迟 | 发请求 → 第一个音频包 |
| 速度 | 端到端延迟 | 用 P50 / **P95**（不用平均值，平均值会掩盖长尾） |
| 记忆 | top-3 召回率 | 固定 50 条问答集，人工标注"正确答案是哪条" |
| 记忆 | 跨端一致性 | 两端各存一份 → 逐条 diff，差异必须为 0 |
| 外观 | 动作可播 | 每个动作名都能在目标形态上播出，无静默丢弃 |
| 外观 | 表情与音频对齐 | 录屏 → 逐帧看口型与音频差多少 ms |
| 工程 | 冷启动时间 | 从点击到能对话 |
| 工程 | APK / 仓库体积 | 打包后实测 |
| 工程 | 新人上手时间 | 找个人，掐表，看照文档能不能跑起来 |

### 3.3 主观评价的样本量（重要，别偷懒）

要把"60% vs 40% 的偏好"检出到 p<0.05（统计功效 0.8），大约需要
**150–200 次独立判断** ≈ **10–15 位听者 × 15 对**。

> **只找 5 个人听 5 对，任何结论都在噪声里。**
> 这不是学术洁癖——是省得你为一个不存在的结果高兴一个月。

判定用**符号检验**（看"选新版的次数"是不是显著多于一半），不是看平均分大小。

### 3.4 可复现性检查

做完一件事，问自己：
- [ ] 换台机器（或换个时间）还能跑出同样结果吗？
- [ ] 别人照文档能复现吗？
- [ ] 我记下的数字是"这一次"还是"稳定的"？（至少跑 3 次取中位数）

## 4. 遇到选择时怎么决定

### 4.1 决策四问

1. **有没有更便宜的验证方式？**（能纸板就别买舵机，能手机就别买相机）
2. **失败会怎样？**（能回滚吗？会丢数据吗？会烧钱吗？）
3. **它是不是别的选择的前提？**（是的话先做它）
4. **我能不能在一两次坐下之内看到结果？**（不能的话，先拆小）

### 4.2 什么时候该写进 ADR

只要满足其中一条，就写进 [`03-架构决议.md`](03-架构决议.md)：
- 以后会有人（包括未来的你）问"为什么当初这么定"；
- 推翻它需要改很多地方；
- 有两个以上看起来都合理的选项，你选了其中一个。

**格式**：`背景 → 选项 → 决议 → 后果`。ADR 写下了就不改，推翻要新增一条。

### 4.3 什么时候该停止一个分支

见 [`00-总体规划.md`](00-总体规划.md) §7 的止损线。
**通用判据**：如果一个分支连续三次尝试都没有产生任何"能给别人看的东西"，
要么换方法，要么停。

## 5. 卡住了怎么办

按顺序试，**不要跳步**：

1. **最小复现**：把问题缩到最小——一个函数、一条数据、一个字段。
   90% 的"玄学问题"在这一步就露馅了。
2. **二分定位**：能跑 A 不能跑 B？把中间那段砍一半，看是哪半边坏的。
   适用于"以前能跑现在不行"（结合 git bisect 更好）。
3. **看边界**：空数据、超长、中文、特殊字符、断网、权限不足——
   长期项目里 80% 的诡异 bug 都在这五种边界上。
4. **写下来**：把"我观察到什么、我期待什么、我试过什么"写成三句话。
   **经常在写的过程中就找到答案了**（这叫橡皮鸭调试，很有效）。
5. **查别人的实现**：去翻 `live2D` 的设计文档——它踩过的坑可能正是这个（**看思路，不看代码**，M9）。
6. **降级**：做一个功能更少但一定能跑的版本。能跑的不完美版本 > 完美但跑不起来的版本。
7. **放到明天**：真的。睡一觉再看的成功率，比硬磕三小时高。
8. **问人**：问同学、发社区、问 AI。问的时候带上第 4 步那三句话。

### 5.1 几个这个项目特有的坑（已知的，别再踩）

| 现象 | 真正的原因 |
| --- | --- |
| 中文路径下 Qt 崩 / 找不到平台插件 | 非 ASCII 路径 + PyQt5 的已知问题，桌面线已有修复代码 |
| 改完配置"不生效" | 配置路径依赖"当前目录正好是程序目录"，桌面线已用 `resolve_path` 中央化 |
| 桌宠跑一会凭空消失 | 个别显卡下 Cubism 原生库导致进程被杀；桌面线已有开关绕过 |
| Python 依赖装不对 | 桌面线有两套解释器（系统 3.10 开发用 / 仓库 `.venv` 打包用），**不能混** |
| Android 后台被系统杀 | 厂商 ROM 激进省电；需要前台服务 + 电池优化白名单 |
| 微信/QQ 突然不回 | 协议/插件变了或 token 过期，先看日志里的原始返回 |

## 6. 一次坐下就能做完的任务（对抗停摆）

长期项目的敌人不是难题，是"今天不知道干什么"。**把待办拆到这个粒度**：

| 太大的任务 | 拆成能一次做完的 |
| --- | --- |
| "把记忆迁到 SQLite" | ① 写出 3 张表的 DDL；② 写一个能读旧 JSON 的解析器；③ 写一个能写进表的函数；④ 用 5 条真实数据跑通一次 |
| "把 Live2D 接进 chatter" | ① 读同学的设计文档并写笔记；② 在 `chatter` 里跑起一个最小 Cubism demo；③ 让一个参数能动；④ 让 act 标签能驱动它 |
| "做 AR" | ① 跑通官方 AR 示例；② 放一个立方体；③ 换成 VRM；④ 让它播一个 idle 动画 |
| "接智能家居" | ① 装 Home Assistant 并打开网页；② 接一个开关；③ 用 HTTP 触发它；④ 让桌宠发这条 HTTP |

**判据**：如果一件事你说不清"做完长什么样"，它就太大了——继续拆。

## 7. 每周自检（五个问题）

1. 这周有**别人能看到**的东西吗？（截图 / 录屏 / 数据 / 提交）
2. 这周的改动有**证据**吗？还是只有"应该没问题"？
3. 有没有哪件事**卡住了**但我没说出口？
4. 我在**等别人**吗？（等硬件、等同学、等设备）——等的这段时间我能做什么？
5. 下周第一件事是什么？**现在能不能直接开始做？**

有任何一个答不上来，先解决它。
