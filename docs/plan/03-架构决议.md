# AIpet 架构决议（ADR）

> 规则：每条 ADR 一旦写下就**不改**，如果后来推翻了，新增一条并标注"被 ADR-00X 取代"。
> 目的：让未来的你（或协作者、或另一个模型）知道"为什么当初这么定"，而不是反复重开同一个讨论。
> 状态：`提议` / `已定` / `已取代` / `搁置`

## ADR-000：把"她"拆成 灵魂层 / 身体层 / 通道层（已定）

**背景**：现在有三条线，每条都自己写了对话、记忆、人格。再加手机、机器人头、机械臂、智能家居，如果继续"每个平台一个全套"，会变成 6 套记忆、6 个人格、6 份 bug。

**决议**：所有平台只做三件事，且分三层：

```
┌─────────────────────── 灵魂层（唯一） ───────────────────────┐
│  人格 / 记忆 / 情绪状态 / 动机 / 关系 / 决策（什么时候开口）    │
│  对外只有两个接口： ① 事件输入   ② 表达意图输出                │
└──────────────────────────────────────────────────────────────┘
        ▲ 事件（谁在做什么、看到了什么）        ▼ 表达意图（说什么/什么表情/什么动作）
┌─────────────────────── 身体层（每平台一份） ──────────────────┐
│  桌面 Live2D / 手机 Live2D / 手机AR(VRM) / 可携带体 / 机械臂 / 家居   │
│                        （家里那台头：以后买成品，先留接口）            │
└──────────────────────────────────────────────────────────────┘
        ▲ 消息                                        ▼ 消息
┌─────────────────────── 通道层（每平台一份） ──────────────────┐
│  QQ / 微信 / 本机 UI / 局域网 / 蓝牙 / MQTT                    │
└──────────────────────────────────────────────────────────────┘
```

**表达意图（Expression Intent）统一格式**——这是让"同一句话同时驱动表情、动作、舵机、灯光"的关键：

```json
{
  "intent_id": "uuid",
  "ts": 1759500000.123,
  "speech": { "text": "你回来啦～", "emotion": "开心", "intensity": 0.7,
              "style": {"rate": 1.0, "pause_bias": 0.1, "nonverbal": ["breath", "laugh_soft"]} },
  "face":   { "expression": "开心", "intensity": 0.7, "sustain_ms": 2000 },
  "body":   [ { "action": "挥手", "intensity": 0.6, "at": {"type": "char", "offset": 0} },
              { "action": "歪头", "intensity": 0.3, "at": {"type": "sec", "offset": 1.4} } ],
  "hw":     [ { "target": "arm",    "cmd": "wave",   "params": {} },
              { "target": "lights", "cmd": "warm",   "params": {"bri": 60} } ],
  "salience": 0.8
}
```

**后果**：
- 每个平台的"身体"只需实现"把 Expression Intent 翻译成自己的东西"（Live2D 参数 / 舵机角度 / MQTT 消息）。
- 换平台不用重写人格与记忆。
- 代价：先要写一层协议和一层翻译器；短期看是"多干活"，长期是唯一能活下去的做法。

## ADR-001：记忆以"服务"为唯一真相源，端上只留缓存（提议 → 待拍板）

**选项**

| 方案 | 做法 | 优 | 劣 |
| --- | --- | --- | --- |
| **M1 云为中心** | 自建云服务（或最小 VPS）持有全部记忆，端只读写 API | 多设备天然一致；换机即用 | 断网即失忆（除非做本地缓存）；隐私外流；月费 |
| **M2 局域网为中心**（推荐） | 家里/宿舍一台常开机器（游戏本或树莓派/N100 小主机）跑记忆服务，端在局域网内读写；出门走内网穿透/Tailscale | 隐私不出内网；零月费；延迟低 | 家里那台必须常开；外网访问要额外配置 |
| **M3 P2P 同步** | 各端本地优先，CRDT/版本向量互同步 | 无中心、离线可用 | 实现复杂度最高；冲突语义难调；手机/单片机不适合 |

**推荐**：**M2 为主 + M3-lite 兜底**。即：局域网内有"记忆服务"时同步；没有时各端写本地 outbox，等下次连上再补传（**离线优先 + 最终一致**）。云只作为"可选的中继"，不存明文。

**为什么不是 M1**：本项目已经有大量隐私资产（摄像头画面、人脸库、聊天记录、作息习惯）。一旦上云，合规成本与心理成本都陡增；而"家里那台常开的电脑"你已经有了（跑桌宠的就是）。

**为什么不是纯 M3**：你要把记忆同步到 ESP32 级别的设备上，让单片机遇上 CRDT 是个灾难。中心服务 + 简单客户端的工程量最小。

**离线优先的最小接口（草案）**

```
GET  /v1/memory/pull?since=<rev>&device=<id>&scopes=state,habits,episodic   → {items:[...], rev}
POST /v1/memory/push  {device, base_rev, items:[{id, type, payload, ts, crdt?}]} → {rev, conflicts:[]}
GET  /v1/event/subscribe?topics=...                                          → SSE 流
POST /v1/intent/emit  {ExpressionIntent}                                     → {ok}
```

**冲突策略（经独立调研修订，[完整报告](04b-调研-记忆架构.md)）**

| 数据类型 | 策略 | 理由 |
| --- | --- | --- |
| 情节记忆（对话/事件/日记） | **append-only 事件日志** | 只追加，天然无冲突 |
| 计数类（互动次数、习惯计数） | **G-Counter**（每端各记自己的增量，合并求和） | 加法可交换，永不冲突 |
| 情感/状态类（心情、精力） | **事件重放 + 本地重算** | 衰减按时间差补算，各端算出同一结果 |
| 单值字段（"主人不吃香菜"） | **LWW-per-field + HLC（混合逻辑时钟）** | 字段粒度，避免整条记录互相覆盖 |
| 人格/角色设定 | **显式版本 + 用户手动解决**（永不自动合并） | 人格是契约不是状态 |

**明确不推荐**：Automerge / Yjs / cr-sqlite 等全量 CRDT。
理由：你的数据形态是「**事件日志 + 少量单值状态**」，不是「多人协同富文本文档」；
Automerge 在 10K ops 时占 8–12MB 堆，对手机与单片机是纯负担。

**另一个关键简化（重要）**：
> **服务端零知识加密 与 服务端向量检索，本质冲突。**
> → 所以**服务端只做加密盲存储 + 转发；检索全部在端上做**。
> 你一年几千条记忆 ≈ 几 MB，端侧全量暴力检索完全够用。
> 推论：**向量永不同步，只同步文本，各端本地重算**（不同端嵌入模型维度不可混用）。

**记忆可见性五级**：`local | device | lan | sync | public`，**默认 `local`**。
**写入时按 type 查规则表决定，绝不由 LLM 决定**（LLM 一旦能决定"这条能不能上传"，隐私就没了）。

## ADR-002：角色包格式统一到 A 线的 `pets/<id>/`（已定）

**背景**：A 用 `pets/<id>/{pet.json,prompt.txt,avatar.png,live2d/,voices/,biaoqingbao/,memory/,portrait_prompts.json}`；
B 用 `assets/pets/<id>/`（几乎同构，缺 live2d/voices）；C 用 `assets/<模型名>/` + `assets/profiles/<模型>.json`（动作/表情档案）。

**决议**：
1. **角色包标准 = A 的 `pets/<id>/` 目录规范**（已验证、有向导、有注册表 `pet_registry.py`）。
2. 把 C（`live2D`，同学张\*泽的项目、只读参考）的 `profiles/<模型>.json`（动作/表情/语义映射）**并入角色包 `pet.json` 的 `motions` / `emotions`**，让"外观能力"与"人格"同处一包。**不新增同职责的档案文件**（`avatar_profile.json` 这类不要再建）。
   - 现状已就位：`pets/murasame/pet.json` 的 `emotions`(:29) / `motions`(:72) 就是这份档案；
     执行器读它（`Live2d/live2d_ui.py:500`），提示词注入也读它（`tool/chat.py:298-335`）。
3. `pets/pet_list.json` 作为跨端清单（手机端可直接读同一份 `pet_list.json` 种子）。
4. 引擎里**不许出现任何角色专有字符串**（A 线已有此原则，继续执行）。
   ⚠ **例外：兜底默认值**。引擎目前仍保留少量硬编码兜底（缺字段时才会用到），这是**已知的待清理项**，不是"已经做到零硬编码"；清单见文末附录 A。

**后果**：以后做机器人头 = 给角色包加 `hardware.json`（舵机映射/表情到舵机的翻译表），而不是改引擎。

## ADR-003：Android 只保留 `chatter` 一个工程；`live2D` 是只读参考（已定，2026-10-04 修订）

> **本 ADR 取代原「以 `live2D` 为基线合并」的版本。**
> 修订原因：`live2D` 是**同学的项目**，不是本项目的分支。

**决议**：
1. **`chatter` 是 Android 侧唯一的主工程**。所有新的 Android 功能一律进 `chatter`。
2. **`live2D` 只读参考**（`00` §0.5 D1/D2）：
   - ✅ 允许：读它的设计文档、理解它的做法、把思路写进 `chatter/docs/` 的笔记里；
   - ❌ 禁止：拷贝它的任何文件（代码/资源/模型/大文件）、把它作为 git 子模块、
     在提交信息里声称"合并了 `live2D`"；
   - ❌ 禁止：让"等同学那边做完/合并"成为阻塞。
3. **要搬的是"做法"，不是"文件"**。落地方式：在 `chatter` 里用 Kotlin 重写一遍，
   并且**能解释每一行为什么这么写**（`02-方法库.md` M9/M10）。
4. **不因为它是参考就降低标准**：Live2D 渲染、act 解析、动作档案数据化这些能力，
   `chatter` 要**全部自己实现**，而不是"等有了再说"。

**当前 `chatter` 的缺口**（要在 `chat` 主工程里自己补）：
- 不含 Live2D 渲染 → 手机上"她"还只是头像；
- 记忆是 App 私有 JSON，与桌面不通；
- 没有动作/表情档案体系。

**理由**：① 那是同学的项目，所有权清楚才不会出问题；② 两个 App 都装手机上用户会困惑"哪个才是她"，
   与其合并两个仓库，不如在主工程里重写；③ 借鉴思路是学习，拷贝文件是负债——
   你会背上一份不敢改、也改不懂的代码。

**代价**：渲染部分要自己写一遍（这是真实工作量）。
**收益**：主工程自洽、没有跨仓库依赖、所有权清楚、你能完全掌控。

## ADR-004：动作/表情以数据档案为唯一来源；双轨形态共用一份档案（已定，2026-10-04 扩展）

**来源**：原则提炼自同学项目 `live2D` 的 `设计文档-动作表情系统.md`（**读它的思路，代码自己写**）。

**决议**：四条原则 + 一条扩展：
1. LLM 只选"名字 + 幅度 + 顺序"，**参数曲线是数据**；
2. 动作对齐台词时间轴，情绪立即生效；
3. act 是隐藏通道，可穿插、可重复，解析用**防御性状态机**；
4. 单数据源：档案 JSON **既喂提示词（技能注入）又喂执行器**；
5. **扩展（双轨，`00` D4）**：档案用**语义键**（`点头`/`挥手`/`扭腰`），
   由各形态的 adapter 翻译成自己的表示：
   - Live2D 形态 → 参数曲线（`ParamAngleY` 等）
   - VRM 形态 → Humanoid 骨骼动画
   - 未来实体 → `hw` 段（哪几路舵机/什么角度）

**后果**：**加一个动作只改数据，不改代码，且所有形态同时获得这个动作。**
这是双轨模型（Live2D + VRM）能成立的前提——否则你要维护两套动作系统。

**注意**：`hw` 段与实体形态是**接口预留**，不是当前要实现的硬件（`00` §0.5 D7）。
现在只写 schema + 一个假驱动。

## ADR-005：语音走"统一语音服务"，不做端上重复实现（提议）

**背景**：A 在本机跑 GPT-SoVITS + F5-TTS（吃显存）；手机端目前无语音；未来机器人头要"本地出声"。
6GB 显存下，"TTS + 本地 LLM + 本地视觉"三者不能同时存在（`01-现状盘点.md` §6 实机探测）。

**决议（提议）**：
1. 在 A 的机器上把 TTS/STT 包成**独立 HTTP 服务**（A 已有 `api.py` + `tool/api_server.py` 的基础 + `localhost:28565` 端口约定）。
   接口现状与规划**要分清**：
   - ✅ **已存在**：`/tts`（`api.py:141`）；
   - 🧭 **规划接口**：`/stt`、`/tts_long`（**目前 `api.py` 里没有这两条路由**）；
   - ⚠ 配置键 `local_api.longtext_tts`（`config.json` / `config.example.json` / `README.md:706` 都有）**目前没有任何代码读取**，
     是一个"写了没用上"的键——要么接线，要么删掉，别当成既有能力。
2. 手机/机器人头默认**调这个服务**；需要离线时再考虑端上小模型（如 Kokoro/Piper 级）。
3. 服务端做**显存仲裁**：一次只加载一个重模型（TTS 或视觉），队列化请求，避免 OOM。
4. 情感/风格参数进接口（`emotion`、`style`、`nonverbal`），与 ADR-000 的 Expression Intent 对齐。

**待拍板**：是否愿意为此把桌宠机器做成"常开家庭服务器"（与 ADR-001 的 M2 是同一个决定）。

## ADR-006：硬件采用"先仿真、后实体，先单点、后整体"（已定）

**决议**：
1. 任何硬件模块，**先在软件里跑通控制接口与数据流**（用假数据 / 仿真 / 可视化），再买零件。
2. 任何硬件模块，**先做单自由度验证**（1 路舵机、1 个传感器、1 个灯），再做整体。
3. 硬件协议**先进 ADR-000 的 `hw` 段**（用 JSON 描述），驱动层再实现，禁止把引脚号写进人格逻辑。
4. 每块板子上电前必须有过流保护与独立供电（舵机绝不从开发板 5V 取电）。

**理由**：这是唯一能让学生党预算不被"买回来发现不匹配"烧掉的做法。

## ADR-007：一切感知数据默认本地、默认可关、默认不留存（已定）

**决议**：
- 摄像头/麦克风/动捕数据**默认不上传**；要上传必须显式开启并在 UI 上常驻可见。
- 原始音视频**不落盘**，只留结构化结果（"检测到主人 0.67"），除非用户显式要求录制。
- 一切被动感知功能（常开摄像头、常开麦克风、动捕）必须有**物理可断**的开关（软开关 + 建议硬开关）。
- 不在仓库/文档/截图里出现真人照片、QQ 号、微信 ID、API Key。

**理由**：`01` 里已发现 `config.json` 含真实 Key；这类事故的成本远高于任何功能收益。合规层面见 `08-风险与合规.md`。

## ADR-008：用"六边形架构"的接口纪律约束三条线的合并（已定）

**决议**：合并过程中，每个模块必须能被归类为：
- **Core**（纯逻辑、无 IO、可在 JVM/Python 单测里跑）：人格压缩、情绪分析、动作曲线求值、调度决策、act 解析
- **Port**（接口定义）：`LlmPort`、`TtsPort`、`SttPort`、`VisionPort`、`ChannelPort`、`BodyPort`、`MemoryPort`
- **Adapter**（具体实现）：OpenAI 兼容 HTTP、Cubism JNI、NapCat WS、iLink、MQTT、串口

**检验标准**：能否给 Core 写单测而不启动 Android/PyQt？不能就说明分层没做到。

## ADR-009：记忆服务"先做出来，静默待用"（已定，2026-10-04）

**背景**：ADR-001 选了方案 A（局域网自建记忆服务）。但直接把它变成运行依赖会有风险：
服务挂了、机器关了、网络变了，都可能导致"她失忆"，进而让你对整套记忆方案失去信心。

**决议**：
1. **服务先做出来，但不作为运行依赖**。达标定义是"**能起来、能 push/pull、能被手动调用**"。
2. **默认关闭**。在**设置页 / 记忆页**留一个入口（`00` §0.5 D3），
   写清"这是电池、暂未启用"，并说明启用后会发生什么。
3. **单机模式必须永远可用**：没有服务时，桌面/手机各自本地读写，功能完整。
4. **服务启用是可回退的**：关掉开关即回到单机模式，数据不丢、不重复。
5. **首次启用要有前置检查**：服务可达、版本匹配、schema 兼容，检查不过就拒绝启用并说明原因。

**为什么这样排**：
- 记忆协议（事件日志 + 物化视图）的价值**不依赖服务存在**——协议对了，导出/导入就能互通；
- "静默待用"让你在**没有运维压力**的前提下把地基打好；
- 未来任何一天想启用，只需打开开关，而不是"再开发一遍"。

**后果**：
- 设置页/记忆页要多一个状态区：`未启用 / 已就绪但关闭 / 已启用`（状态必须真实，不许"看着是开其实没生效"）
- 验收指标里"静默记忆服务"这一条 = 能起来 + 能 push/pull + **默认关闭**（见 `00` §5）
- 这也是止损线里的退路：万一同步冲突修不好，退回单机模式即可（`00` §7）

## ADR-010：可携带体做成「核 + 可换的皮」，接口必须标准化（已定，2026-10-04）

**背景**：用户明确要"可拆卸、可多个"——核（摄像头/麦克风/喇叭/定位/联网/电池）
要能在**毛绒玩偶**与**人形娃娃**之间换装，以后还可能有更多外形（`00` §0.5 D11/D12）。

**决议**：
1. **结构分两层**：
   - **核 Core（一个）**：所有传感器、输出、电池、身份；
   - **皮 Skin（多个，可替换）**：只有外形与开孔，**不含电子件**。
2. **物理接口标准**（要冻结下来，写进 `hw` 契约）：
   - 核的最大外型尺寸与固定方式（磁吸 / 魔术贴 / 卡扣）；
   - 开孔位置与最小尺寸：摄像头、麦克风、扬声器；
   - 供电与充电方式（核自带电池，**不从皮取电**）；
   - **指示灯的可见位置**（隐私要求：不能把 LED 藏在皮里）。
3. **软件接口标准**：
   ```
   核 = { device_id, skin_id?, sensors[], outputs[], battery, network }
   ```
   - **`device_id` 属于核，不属于皮** → **换皮不换身份**；
   - 换皮后**记忆必须连续**（还是同一个她）；
   - 皮可以有 `skin_id` 用于外观/语音风格微调，但**不改人格**。
4. **买皮的三条判据**（`00` §4 方向 3.3）：能拆开、内腔够放核、能不用它自带的电子件。
5. **禁止**：把核的功能实现在皮里（那会让"换皮"变成"换设备"）。

**后果**：
- 好处：一个核多种外形；买皮远比做皮便宜；坏了换皮。
- 代价：核的尺寸被**最小的那个皮**限制（要按最紧的腔体设计）。
- 与 D7 的关系：**买现成的皮/核不算手搓**，现在就可做；自制外壳排在三年后。

## ADR-011：手机端以 Android 为准，并**准备一台专用 Android 测试机**（已定，2026-10-04）

**背景**：主测试机是 **华为 nova 13 Pro，鸿蒙 4.2**（`00` §0.5 D16）。
而该机型在 **HarmonyOS NEXT（原生鸿蒙）Beta 名单**内；**原生鸿蒙不运行 Android APK**，
需借助卓易通之类兼容层，且不是稳定保证。
同时 `chatter` 是 Kotlin/Compose 的 **Android 应用**，微信 ClawBot 通道正常（D17）。

**风险**：主力机某天升级原生鸿蒙 → **`chatter` 装不上 → 手机端开发直接停摆**。

**决议**：
1. **`chatter` 继续走 Android 路线**（不因一台机器的系统变化就换技术栈）。
2. **准备一台专用 Android 测试机**（便宜的二手即可）。
   - 好处：主力机随便升级，开发环境固定在 Android 上；
     它还能**兼作可携带体的原型机**（D11 的"先用手机当身体"）与 AR 实验机。
3. **不建议**为了主力机去做鸿蒙原生版本（ArkTS/ArkUI）——
   那等于把"做一个 App"变成"维护两个平台的 App"。
4. **验收项**：`chatter` 能在**专用 Android 测试机**上构建、安装、跑通微信收发。

**后果**：
- `05-采购与预算.md` 增加一项"二手 Android 测试机"。
- 如果将来真要支持鸿蒙原生：作为**独立的新工作**评估，不混进当前路线。

## ADR-012：`live2D` 的复用边界——**思路可复用，代码与资源不可照搬，SDK 另有授权**（已定，2026-10-04）

**背景**：用户要求"`live2D` 里应该有许多可以融合的部分，可以复用最好"（`00` §0.5 D25）。
同时 `chatter` 里**已经有一份** `docs/LIVE2D_EXTRACTED_IDEAS.md`，
且其中**思路 1–5 已全部落地**（`PendingInbox.kt`、合并上限、安静时段、时间感知、后台回复通知，已在源码核实）。
> ⚠ **注**：那份 md 的**状态列已经过期**（仍写着"待做/尚未落地"），**以源码为准**（见文末附录 B 的核实清单）。
另有一条**独立的合规约束**：Live2D Cubism SDK 有自己的发布许可合同（`00` §0.7）。

**决议**：把"复用"拆成四层，**每层的规则不同**：

| 层 | 能不能复用 | 怎么做 | 依据 |
| --- | --- | --- | --- |
| **① 思路 / 设计** | ✅ **尽量复用** | 读它的 `设计文档-动作表情系统.md`、`优化方案.md`、`修改记录.md`，把结论写成 `chatter/docs/` 的笔记 | D25；`02-方法库.md` M9 |
| **② 我们**写的实现 | ⚠ **重新实现** | 在 `chatter` 里用 Kotlin 自己写；**不引入它的任何文件** | ADR-003（它是同学的项目） |
| **③ 模型资源**（`.moc3` / `exp3.json` / 贴图） | ❌ **不拷**（除非有明确授权） | 自己准备模型；或使用有明确许可的免费模型 | `08` §1.5 版权 |
| **④ Cubism SDK 本体** | ⚠ **可以用，但受 SDK 许可约束** | **不提交到仓库**；写清"请自行从官网下载并同意其许可" | **下方"SDK 授权"** |

**关于 ④（本节的重点，也是我先前漏掉的一条）**：

**先分清三件完全不同的东西**（这条最容易混）：

| | 是什么 | 谁的 | 和同学的关系 |
| --- | --- | --- | --- |
| **模型文件**（`.moc3` / `exp3.json` / 贴图） | "她长什么样"的数据 | 角色原权利人（柚子社、しらたまこ 等） | 他项目里也有，但**也是网上来的** |
| **Cubism SDK** | 让程序**能读模型文件并画出来**的官方开发库 | **Live2D 株式会社**（专有软件） | 他项目**用了它**，但不是他的 |
| **同学的代码** | 他自己的实现（`JniBridgeC.cpp` 等） | 你同学 | 就是他的 |

> **所以"Live2D Cubism SDK 是不是我同学的？"——不是。**
> 它是 **Live2D 公司**的软件。同学的项目只是**使用了**它（就像你俩都用 Qt 一样，Qt 不是你们的）。
> 这跟"模型是网上下载的"是两回事：**模型 ≠ SDK**。

- 已核实：公开发布**使用 Cubism SDK 制作的作品**（注意：是"**用 SDK 做的作品**"，
  不是"发布模型文件"），原则上需签 **SDK 发行许可证**；
  **自用/开发阶段不需要**；"小型企业/普通用户"年销售额低于 1000 万日元时也不需要，
  **但"可扩展性 APP"（虚拟化身 + 可扩展功能）例外——任何规模都要逐个作品单独签**
  （[官方帮助](https://help.live2d.com/zh-CHS/sdk/sdk_001/)）。
- **我们的项目恰好是"可扩展性 APP"**（她是虚拟化身 + 有插件/换皮/多形态）。
- 官方还明确列了**另一种不需要签**的情况：**发布的内容不是用 SDK 做的**
  （例如从 Cubism Editor 导出的视频）。→ **想展示时可以走这条路。**

**因此的执行规则**：
1. **本地自用**：属于"试用和开发阶段"，**什么都不用做**；
2. **对外展示想零风险**：发**视频/截图**（不是用 SDK 做的作品），而不是发 APK；
3. **不要公开分发含 SDK 的 APK**，除非先确认套餐并签好
   （[发行许可说明](https://www.live2d.com/zh-CHS/download/cubism-sdk/release-license/)）；
4. **仓库里不提交 SDK 二进制**——这条还有第二个理由：**本仓库是 AGPL-3.0**，
   而 **Cubism SDK 是专有软件，两者的分发条款存在冲突**（把专有二进制和 AGPL 代码一起分发是**双向**的麻烦）；
   写清"请自行从官网下载 SDK 并同意其许可"即可；
5. 将来真要发布：先去问[学生优惠](https://help.live2d.com/zh-CHS/student/student_01/)；
6. 详情与选项见 [`07-待定选择支.md`](07-待定选择支.md) **Q22**。

**⚠ 另有一条独立的、而且更紧迫的资产问题**（与 SDK 无关，属于 `08` §1.5 素材版权）：

> **实读发现**：桌面仓库**已经关联了公开远程**
> （`origin = github.com/sensei142563/AIpet-Murasame.git`），
> 且**角色模型与立绘已被 git 跟踪**（`pets/murasame` 171 个文件、`pets/natsume` 155 个、
> `pets/noir` 47 个，含 `.moc3` 与 4096 贴图，是全仓最大的文件）。
> `.gitignore` 已排除 `pets/arona`、`pets/hiyori`，说明这条意识是有的，
> 但 `murasame`/`noir`/`natsume` 仍在库里。
>
> **要点**：这些来自商业作品的资产，**一旦推送到公开仓库就等于再分发**。
> 这与"有没有公开发布 Live2D 模型"是同一件事的另一面——
> **模型不是"你发不发"的问题，而是"它已经在库里、推不推"的问题。**
>
> **现状**：`COPYRIGHT.md` §五 已如实声明来源与"仅限学习交流、禁止商业用途"，
> 这一点做得对。**但声明不等于授权**——是否推送公开仓库由用户决定
> （`docs/handover/README.md` 原则 1：不推送、不动远程，除非用户明确下令）。
> 处置建议见 [`08-风险与合规.md`](08-风险与合规.md) §1.5。

**后果**：
- 复用**思路**没有障碍，而且 `LIVE2D_EXTRACTED_IDEAS.md` 已经证明这条路走得通；
- 复用**代码/资源**会同时踩三个坑（同学的所有权、模型版权、SDK 许可）——**不做**；
- **不阻塞任何开发**：自用状态下的规则是"照做即可"。

## 附：记忆架构的四条"必须遵守"（摘自独立调研，[全文](04b-调研-记忆架构.md)）

1. **统一抽象是「事件日志 + 物化视图」**，不是「一个大 JSON」。
   `history.json` / `long_history.json` 这种整文件读写**必须退化为导出格式**，不能当主存储。
2. **不要引入 Mem0 / Zep / Letta 作为运行时**——它们是记忆层/Agent 运行时，
   而两个代码库已有自己的 LLM 调用、人格 prompt、检索逻辑；引入等于重写编排层。
   **抄它们的架构模式，不抄它们的部署。**
3. **人格是契约，不是状态**：永不参与同步；一致性检查失败时**告警 + 回退到备份副本**，
   **绝不因此拒绝启动**（全仓目前**没有任何 sha256 校验**；既有启动设计是"宽容降级"——
   `pets/pet_registry.py:79-112` 读失败时**绝不动盘**、内存兜底返回上次成功清单；
   `pet.json` 还会被 `pcl_launcher/pet_wizard.py`、`portrait_studio.py` 正常改写）；
   LLM 不得改写人格核心；定期采样算人格向量余弦，低于阈值告警。
4. **最大的技术风险不是同步，是记忆污染**：LLM 幻觉写进长期记忆后会自我强化。
   必须两阶段写入（`candidate → active`，≥2 次独立证据或用户确认才生效）+ 强制 `source_event_ids`；
   抽取时区分 `claim_type: stated | inferred`，`inferred` 默认置信度 ≤0.5 且**禁止写入用户画像**。

**检索打分公式（建议直接采用）**
```
score = 0.45·relevance + 0.25·importance + 0.15·recency + 0.15·rrf_norm
recency = 0.5^(Δh / 168)        # 半衰期一周
再用 MMR(λ=0.7) 去重
```
> **术语**：**三路召回** = 语义向量 / 关键词 BM25 / **结构化精确匹配**；
> 上面的 `importance + recency + MMR` 是**重排层**，**不要叫"第三路"**。

**对 `live2D`（同学张\*泽的项目、只读参考）`MemorySearch.kt` 的评审**：
RRF 用 `1/(60+rank)` 是正确的，**可作参考**；缺的是——
① 三路召回里少一路：**结构化精确匹配**；② **BM25 必须补 IDF**（现在注释写"忽略 IDF，语料小"，
到 5000 条时"主人/本座"这类高频词会主导排名）；③ **重排层**：时间衰减 + 重要性 + MMR。
⚠ 这些都要在 **`chatter`** 里用 Kotlin **重写**（ADR-003），不是"改造 C"。
