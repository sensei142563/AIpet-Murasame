### 3.1 NapCat 4.18.28 实测：✅ 通过（用户 2026-09-24 日志）

用户提供了两段真实运行日志，结论：
- 扫码登录成功 → `NativePacketClient Hook 初始化成功 platform=win32.x64`
  （**没有**出现旧版本那句「PacketBackend 不支持当前QQ版本架构」）
- OneBot11 WS `127.0.0.1:3001` 已启动，`[QQBridge] ✅ WebSocket 已连接`
- 私聊收到「测试」→ 回了 7 条文字 + 1 张图 + 1 条语音 → **收发链路完全通**
- 启动横幅里能看到新的版本自检输出（`[版本] ✓ NapCat 4.18.28 与 NAPCAT_VERSION.txt 一致`）

顺带从日志里发现并修掉的两个老问题：
- **语音识别（STT）其实一直没工作**（`32ef6e6`）：`[STT] ⚠ 模型预热失败: Cannot find an
  appropriate cached snapshot folder ... outgoing traffic has been disabled`。根因是
  "找模型的目录"与"模型实际所在目录"不一致 + 无条件锁离线。修完在本机实测
  `warmup() → True`（16.2 秒加载）。
- **每次启动的假丢消息警报**（`a319f2e`）：`⚠ 活性探测 发送失败：连接尚未建立（累计 1 次发送失败）`
  + `🔗 已重新连接（此前断线期间 1 次回复未送达，请对方重发）`。其实是启动瞬间的探针
  在 WS 建好之前发出；一条回复都没丢。现在控制类调用不计入"未送达"，且未连上不发探针。
- 日志里 `⚠ GPU 初始化失败，使用 CPU` 属正常回退（该机 CUDA 不可用），不算问题。

### 13.2 Live2D 画布"崩坏 / 频闪"的真正根因（`d57ca2d` 只是绕开，没治本）

用户复现：工坊→预览窗口（正常）→关掉→调试器 = **频闪**；重启桌宠后 工坊→调试器（黑画布）→预览窗口 = **崩坏**。
关键前提：**启动器一个进程里最多同时有三个 Live2D 画布** ——
① 立绘工坊里那块**内嵌**预览（角色没有 2D 素材时显示 Live2D，用户日志里 `[PCL] Live2D 模型加载成功` 就是它）
② 「打开实时预览窗口」的独立窗口 ③ 动作/表情调试器的 `ModelCanvas`。

根因：Cubism 原生引擎是**进程级全局单例**，`LAppModel` 的 GL 资源绑在**第一个**建立起来的 GL 上下文上；
后建的画布在自己的上下文里画不出东西（实测帧缓冲**模型墨迹 0.0%、帧间跳变 0.0%** = 完全空白/冻结）。
`probe_l2d_two_canvases.py` 三种画布同时开的实测：

```
SHARE=False（改前）: 画布1内嵌 墨迹 40.3% 动  |  画布2预览 0.0% 冻  |  画布3调试 0.0% 冻  |  画布2复测 0.0%
SHARE=True （改后）: 画布1内嵌 40.3% 动        |  画布2预览 39.8% 动 |  画布3调试 29.1% 动 |  画布2复测 40.6% 动
```

修法：入口在**创建 QApplication 之前**打开 Qt 的共享 GL 上下文开关
（`silicon_ui.enable_shared_gl_contexts()`，silicon_window.launch / debug_live2d.py 各调一次）。
窗口摆到 (-4000,-4000)：真实 GL 上下文（offscreen 平台起不了 GL）但不出现在屏幕上；
判据用 `grabFramebuffer()` 的"模型墨迹"（与画布清屏色差得多的像素占比）+ 帧间跳变，
**不能用"非黑像素"**（清屏色本身是深色，非黑占比恒 100%，量不出模型画没画出来）。

### 16.1 纠正一处我自己的错误判断（"exe 故意不用系统 Python"）

我最初把"代码形状"当成了"设计意图"，说成"冻结版故意面向没装 Python 的用户"。这与事实不符：
README 的教程第一步就是装 Python 3.10，`install.bat` 是官方第一步。查证：

- `_find_python` 是整合提交 `2725311` 带进来的，**之后一次没改过**；
- 它原来只有 ①②两个候选，打包版直接 `return ""`；
- **但它自己的报错文案写的是"启动器需要 runtime\venv 或系统 Python"** —— 文案承认系统 Python 可用，代码却从不返回；
- 三个 bat（桌宠/QQ/微信）**都会**回落系统 Python（`set "PYTHON_CMD=python"`）并带依赖探针；
- 第二个候选 `<exe目录>\python.exe` 与安装器布局也对不上（安装器的便携解释器在 `app\python\python.exe`）。

⇒ 结论：**是漏了回落 + 文案与行为不一致**，不是设计。修法（用户拍板"加回落"）：

```python
PET_NEED = ("PyQt5", "torch")          # ← 与 启动桌宠.bat 的 find_spec 探针同一套口径
QQ_NEED  = ("websocket", "requests")   # ← 启动QQ.bat
WX_NEED  = ("requests", "Crypto", "qrcode")   # ← 启动微信.bat
_find_python(base, need):  ① runtime\venv ② 包内 python.exe
                           ③ 源码模式 → sys.executable
                           ④ 打包版 → PATH 上的 python/python3，**先过 _python_has() 依赖探针**
```
`_python_has()` 用 `importlib.util.find_spec` 只查不导入（毫秒级、不触发 DLL），
`CREATE_NO_WINDOW` 避免探测时闪黑框。探针不过就交给 `_require_python()` 报**准确**原因：
"系统里找到 Python 但缺依赖（需要 PyQt5、torch）→ 去跑 install.bat"，不再指向"缺文件"。

⚠ 这个回落只对"系统 Python 里已经装好依赖"的机器有效（开发机立刻就能用）；
**全新用户的机器仍然要跑一次 `install.bat`**，否则探针会拦下并给出指引 —— 它不是"免安装"的替代品。
真要"解压即用、不需要 Python"，那是**一键安装器**那条路（载荷里带 `app/runtime/venv` + `app/python/`，
安装时改写 `pyvenv.cfg` 指向随包 python），代价是包 +约 1.8 GB。

## 17. 绿色版实测第二批：桌宠"卡退"与微信"秒卡退"（两个互不相干的真 bug）

用户拿到重打的绿色版再测，报"启动到 CUDA 检测那行就卡退，微信秒卡退"。查证结果：
**两条都是真 bug，而且与打包无关**（源码树里同样复现），根因完全不同。

### 17.1 桌宠"卡退" = PyQt5 自带的旧 MSVC 运行时 vs 新版 torch（0xC0000005）

**证据链**（没有靠猜）：

1. 用户日志停在 `[AIpet] 检测到 CUDA 环境: 驱动 591.91，CUDA 13.1`，无 traceback；
2. Windows 事件日志（19:11 / 20:03 / 20:10 / 20:12 共 4 次，与测试时间吻合）：
   ```
   出错应用程序： python.EXE 3.10.4
   出错模块：     MSVCP140.dll 14.26.28720.3
   异常代码：     0xc0000005，偏移每次都是 0x12ea0
   Faulting 模块路径： …\site-packages\PyQt5\Qt5\bin\MSVCP140.dll
   ```
3. 无头复现（`python -c`，同样的解释器）：
   ```
   只 import PyQt5          → OK
   只 import torch          → OK (2.11.0+cu128)
   先 PyQt5 再 torch        → 崩（exit=1，OSError WinError 1114 loading torch\lib\c10.dll）
   先 torch 再 PyQt5        → OK
   ```
   项目 `.venv` 里同样崩（torch 2.12.0）。
4. 版本对照：PyQt5-Qt5 **5.15.2** 在 `PyQt5\Qt5\bin` 里带了一整套 **14.26（VS2017）** 运行时；
   系统 `System32` 的是 **14.51（VS2022）**；torch ≥2.x 的 `c10.dll` 需要新的。
5. 崩溃点精确到行：`run.py` 第 208 行 `import PyQt5.QtCore`（依赖自检）先把旧运行时
   拉进进程，第 474 行才 `import torch` → 必崩。**`main.py` 本来就是 torch 先、Qt 后**
   （注释里写着"本地模式要求在任何第三方库之前导入"），所以只有 `run.py` 这条路必崩；
   启动器只有 Qt，所以它一直没事。

**修法**（新增 `tool/msvc_runtime.py`）：
把 `PyQt5\Qt5\bin` 里那 6 个**旧于系统**的文件
（`msvcp140 / msvcp140_1 / msvcp140_2 / vcruntime140 / vcruntime140_1 / concrt140`）
改名成 `*.aipet-disabled` 让位，Windows 就会用系统的新运行时。
护栏：只动"系统确实有更新版本"的那一个文件（否则 Qt 可能缺依赖）；幂等；纯改名、可回滚；
Qt 自己的 DLL（Qt5Core.dll 等）绝不碰。接线：
- `run.py`：在**第一次 import PyQt5 之前**调用（否则旧运行时已经进进程了）；
- `install.bat`：装完依赖多一步 `[4.5/5]` 调用它（新装的 venv 一次到位）；
- 手动：`python -m tool.msvc_runtime [--dry-run]`。

验证：改名后 `import PyQt5.QtWidgets` + 建窗口渲染 + `import torch` + `import cv2` 同进程 exit=0
（系统 Python 与 `.venv` 都已就地修好）。

⚠ 注意：这不是"打包引入的问题"，而是**PyQt5-Qt5 5.15.2 + 新版 torch 的版本冲突**，
只要一个环境里同时有这两者、且 Qt 先加载的人都会中招（用户的开发机也一样）。

### 17.2 微信"秒卡退" = `get_config()` 遇到缺失的 config.json 直接抛异常

复现（在包目录里直接跑）：`run_wechat.py` 第 249 行 `cfg = get_config("./config.json")`
→ `tool/config.py` 是**裸 open()** → `FileNotFoundError` → 进程立刻退出（控制台一闪就没，

1. `tool/config.py`：
   - `get_config()` 改为**缺失/损坏时回退到同目录 config.example.json 的默认值**并打印一次提示。
     用示例而不是空 dict 是故意的：调用方大量 `get_config(...)["model_type"]` 这样**下标访问**，

### 18.2 编码不安全打印：系统排查结论

新增 `audit_gbk_prints.py` 扫全仓库：**33 个文件**在"没有自带 UTF-8 守卫"的情况下打印非 GBK
字符。但逐个核对后绝大多数是**误报** —— 它们都跑在带守卫的进程入口里（真控制台是 UTF-8，
只有重定向/管道才退回 GBK）。

真正危险的是"**没有入口守卫的调用点**"：

| 调用点 | 风险 | 处置 |
| --- | --- | --- |
| `.bat` 里的 `python -c "..."`（install.bat / 启动*.bat / 重启长语音服务.bat） | 被调代码打印 ⚠ 之类字符 → 安装或启动这一步直接失败 | 5 个 bat 统一 `set "PYTHONIOENCODING=utf-8"` |
| 会被 `python -c` 直接落到的库模块（`tool/config.py`、`tool/msvc_runtime.py`） | 同上 | 模块顶部加标准 stdout/stderr 守卫（幂等） |

⚠ 一个**自我纠正**：我最初给 bat 加的是 `PYTHONIOENCODING=utf-8` **加** `PYTHONUTF8=1`。
后者会开启 Python 的 UTF-8 模式，把 `open()` 的**默认编码**也改掉 —— 而本项目存在 GBK 文件
（`requirements.txt`），等于为这个坑挖另一个坑。已把 `PYTHONUTF8=1` 全部撤掉，只留
`PYTHONIOENCODING`（只影响 stdio），并在自测里钉住"**不许**误设 PYTHONUTF8=1"。

`test_entry_console_guard.py` 追加两组断言：bat 的编码保险 + `run.py` 的两道防线顺序。

### 18.3 MSVC 冲突的第二道保险：加载顺序

`tool/msvc_runtime.py` 的自愈是治本，但前提是**系统里存在更新的 VC++ 运行库**。没装运行库的

## §22 两个本机环境事实（2026-09-28 实测，下次别重踩）

1. **连一个没在听的回环端口不会立刻被拒**：裸 `socket.create_connection(("127.0.0.1", p), 1.5)`
   要 1.511s 才 `TimeoutError`，`urllib` 1.501s 才 `URLError`（像是安全软件静默丢 SYN）。
   后果：任何"连一下试试"的探活都会白赔一个超时。判断本机端口有没有人在听，用
   `bind` 试探（失败 = `EADDRINUSE` = 有人在听）是 0ms 的，比 `connect` 强。
   脚本：`_audit_fish9269/probe_local_connect.py`。
2. **`tool/cloud_API_chat.py` 在导入期就读配置**（第 12 行
   `get_config("./config.json")["local_api"]["cloud_api"]`）：cwd 不是程序目录时连
   `config.example.json` 都找不到，直接 `KeyError: 'local_api'`。所以任何 import 它的
   探针必须先 `os.chdir(<仓库根>)`。这是既有脆弱点，尚未改（改它要动 hot 文件，单独一步做）。

数据落点（都在 `pets/<角色>/memory/`，互不覆盖）：`state.json` 心情好感、`habits.json` 习惯、
